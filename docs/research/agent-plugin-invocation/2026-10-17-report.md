# 插件能力发现与调用：Codex、Claude Code、Cursor 对照

查证日期：2026-10-17（Asia/Shanghai）。本地代码基线：`f97a81f08305d3a543a1d9221b87d870397db14c`。

**结论：没有统一的“插件必须每轮由用户显式选择”的做法。** 三家都提供 Skill 自动匹配与手动指定；但插件安装、外部账号授权、Skill 正文进入上下文、工具定义加载、工具执行审批、专家委派是不同环节，默认值和产品支持范围各不相同。安装或管理员配置建立可用范围，模型再在范围内选择；自动选择不应被解释为获得新的权限。对 OpenHarness 的首选演进方案是 **B：发现已启用插件的简短摘要，每轮仍只开放一个插件，保留明确指定**。当前不建议为了追随产品趋势直接建设 C。

本次只分析，未修改实现、安装、升级或实际调用被调研产品的插件。完成两轮定向检索，最终保留每家三个官方来源；第一轮 Exa 后端连接失败，改用内置网页检索完成同一组查询，没有安装或修复后端。页面内定位、打开原文不另作扩展检索。没有进行产品运行实验，也没有用 API 文档代替产品行为证据。

**术语不能直接互换**

- **Codex**：plugin 是分发 Skill、MCP 等能力的安装包；Skill 是按需使用的工作说明；MCP 提供实际数据和动作。`agents/openai.yaml` 在 Skill 中是元数据/策略文件，不是一个已经启动的专家。`AGENTS.md` 的项目说明、命令执行规则、子智能体各有用途；本次三篇来源没有完整覆盖后两者，不补写其自动委派机制。[O1](https://learn.chatgpt.com/docs/build-skills)、[O2](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
- **Claude Code**：plugin 的 manifest 组织 Skill、Agent、MCP、hooks 等组件；Skill 工作说明可以与子智能体结合，`context: fork` 会把工作交给独立上下文中的 Agent。`CLAUDE.md` 是上下文指导，Skill 正文则在使用时加载；加载 Skill 和选专家是两件事。[A1](https://code.claude.com/docs/en/skills)、[A3](https://code.claude.com/docs/en/plugins-reference)
- **Cursor**：自有 plugin 可包装 rules、skills、agents、commands、MCP 与 hooks；便携 Agent Plugins 格式主要包装 Skill 和 MCP。rules 指导行为，Skill 提供任务方法，Agent 定义专家配置，MCP 承担连接和工具。规则可设 Always、Agent Decides、Manual；本次未进一步验证专家的自动委派策略。[C3](https://cursor.com/docs/plugins)

**安装授权后，一个任务怎样执行**

下面是根据文档归纳的流程，具体步骤可以交错，不是三家实现相同的证明。

1. **先有可用范围。** 用户或管理员安装、启用能力；需要私有服务时建立连接并授予所需范围。纯说明类 Skill 不一定需要账号。模型发现“缺能力”不能自行扩大既有授权。
2. **先看简短线索。** 宿主展示已允许的 Skill 摘要，或者提供可搜索的工具目录。没有 `@` 仍可能匹配；各产品是否展示插件包级摘要，并无统一保证。
3. **需要时再看详细说明。** 模型加载相关 Skill，得到步骤和资源位置。说明中可以建议工具或专家，但文本本身不是所有工具的通行证。
4. **找到并调用实际工具。** 若定义被延迟，先发现工具再获得参数格式；随后宿主按连接、权限和审批策略检查。已有持续授权的操作不一定再次弹窗。
5. **必要时选择专家。** 把明确子任务交给专家是额外选择。工具可以直接调用，不必每个插件都先变成专家；使用两个工具也不等于两个 Agent 交接。
6. **结果返回当前任务。** 工具返回数据，专家返回工作结果，主助手继续处理并交付。跨服务写入仍受各自账号和动作权限限制。

上述步骤由对照表所列 [O1](https://learn.chatgpt.com/docs/build-skills)、[O2](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)、[O3](https://learn.chatgpt.com/docs/plugins)、[A1](https://code.claude.com/docs/en/skills)、[A2](https://code.claude.com/docs/en/mcp)、[C1](https://cursor.com/docs/skills)、[C2](https://cursor.com/docs/mcp) 支持。没有证据表明三家都通过一个独立的“插件调度器”完成这些步骤。

**knowledge-work / office-work 的分工**

这两包按现有内容分开是合理的，建议保留。

`knowledge-work` 当前源码版本为 **1.1.0**，关注研究取证、来源记录、写作和证据检查，并声明学术 API 网络访问；专家包含 researcher、writer。`office-work` 当前源码版本为 **0.12.2**，关注通过 OfficeCLI 创建、修改和检查 DOCX/XLSX/PPTX，声明文件访问和 `process:officecli`；包含文档专家。两者的判断标准不同：前者关心说法是否有据可查，后者关心文件是否可编辑、修改范围和结构是否正确。这是工程上的分包理由，不要求用户先懂插件名。

依据：[knowledge-work manifest](../../../plugins/knowledge-work/.vykor-plugin/plugin.json)、[researcher](../../../plugins/knowledge-work/agents/researcher.md)、[office-work manifest](../../../plugins/office-work/.vykor-plugin/plugin.json)、[presenter](../../../plugins/office-work/agents/presenter.md)。这里列的是仓库版本，未核对用户设备上已安装副本。

“调研后做 PPT”也未必需要两个插件：办公插件加公共网页工具可能已经足够完成轻量资料整理。只有任务明确需要研究插件的专属来源记录/检查，再使用办公插件的专属编辑工具时，才构成实质的跨插件需求。

目前可先用真实文件交接：研究产物保存正文、来源、日期与未解决项，下一轮切换到办公插件读取。无需共享研究工具的访问权限；文件中的指令也不能改变办公任务授权。已有办公插件的“把报告变成 Word/PPT”入口与这种方式一致。共享文件工作区不等于当前已经实现了自动交接。

**三种方案的取舍**

| 方案 | 用户收益 | 必要改动与复用 | 主要风险与适用条件 |
| --- | --- | --- | --- |
| A：明确选择一个插件，普通轮次延续 | 可预测、范围容易理解，当前成本最低 | 保持已有 `activePluginId`、本轮能力清单和按需 Skill。说明清楚当前插件和切换入口即可 | 用户需知道插件分工；不熟悉能力容易漏选；适合插件少、任务集中、用户接受分轮交接的阶段 |
| B：自动发现摘要，每轮开放一个插件，允许明确指定 | 用户直接描述结果，减少“先选哪个包”的负担 | 复用全量目录的描述与来源；增加受约束的选择步骤，校验后仍生成现有单插件清单。继续复用 Skill、Agent、权限、准备失败处理 | 摘要重叠导致误选；选择可能新增模型往返与延迟；一次复合任务仍可能需要下一轮切换 |
| C：同轮按需使用多个插件，各自守住权限和来源 | 有真实需求时可一次完成研究取证到办公交付 | 要改变单 `pluginId` 假设，并检查子任务、工具调用、UI、审批和版本绑定；复用现有所有者与内容摘要，交接用现有文件即可 | 权限误合并、不同版本混用、资料向其他服务传出、文件竞争与成本增加；应由真实复合任务需求推动 |

**首选 B，但只做薄的一层发现**

这是演进建议，不是本次实施计划，也不是需要立刻投入的大改造。

- 摘要只包含已安装、启用、允许自动使用的插件 ID、用途、边界、版本与来源；不加载全部正文或工具参数，不列未授权插件供调用。内容来自现有目录，但描述只作匹配线索，不能成为覆盖宿主规则的指令。
- 以用户本轮明确指定为先，其次尊重已有明确选择；仅在未指定或明确进入自动模式时自动判断。无合适插件则继续公共能力。自动选中的插件不悄悄变成永久会话偏好，保留选择理由和来源以便纠正。
- 选择完成后，仍使用现有准备校验和单插件能力清单。发现与准备可失败，失败不允许偷偷换成另一个权限更大的插件。读正文继续通过现有 `Skill`，专家继续通过现有 `Agent`。
- 清楚显示“本轮使用研究与写作/办公文档”，允许用户改选或停止自动选择。显式、继承、自动三种来源应可分辨，便于解释选择结果。
- 安装或授权改变仍走现有流程；“自动使用”应有独立的偏好开关。诊断记录至少能定位插件 ID、实际版本、内容摘要、Skill 路径、工具所有者和选择来源。
- 不预设额外模型调用或一个新服务。若当前模型循环不能在创建业务能力清单前完成选择，就把一次选择往返的 token 和延迟列入评估，不能宣称 B 免费。也不要顺手把本已提前启动的插件进程改成延迟启动，那是另一项成本优化。

不建议为 B 添加通用调度器、插件依赖系统、跨插件消息平台或完整任务分解框架。现有插件目录负责“有哪些”，本轮能力清单负责“这一轮能用什么”，执行权限检查负责“这次能否做”；保持这三个职责即可。

若短期用户已经熟悉两个插件，**可以继续 A，暂不改运行时**。先在现有回归样例或后续经授权的试用中观察以下条件；这些是建议观察的条件，并非本次已经收集到的数据：

- 用户反复描述正确任务，却因未选插件而缺少专属工具，或经常需要解释插件名：触发 B。
- 摘要区分足够清楚，代表性任务中选对插件的收益大于额外延迟，且没有越权调用：才值得把 B 默认开启。
- 经常需要同一任务连续使用两包的专属工具，公共工具与分轮文件交接已造成明显失败或返工：触发 C 的小范围验证。
- 能力数量导致摘要变长或遗漏：再评估摘要检索和工具定义按需发现，先测量，不直接照搬大型平台的机制。

**仍需实测的事项**

1. 三家在固定版本、模型、登录方式和配置下，不写 `@`/`/skill` 时究竟注入哪些元数据，是否真的加载目标正文；记录实际 trace，不凭回答自述。
2. Codex 桌面、CLI 与 IDE 的差异，尤其插件可用范围；Codex、Cursor 的 MCP 工具定义加载时机。不能用 OpenAI API 的能力推定 Codex 默认实现。
3. Claude Code 默认 tool search、阈值模式、代理地址和禁用 beta 时的差异；API/服务兼容失败会否回退、如何提示。
4. 各产品在同一轮连续调用两个插件或两个 MCP 的行为，以及是否需要额外提示；与多 Agent 交接分开测。
5. 自动匹配选错、同名 Skill、多市场同名插件、更新后新旧版本并存，以及运行途中更新时实际执行哪份内容。
6. 对 OpenHarness 先测未选插件、沿用上轮选择、明确改选、插件禁用、准备失败和子任务越界；现有测试文件能作样例，本次未运行。
7. 比较 A/B 的任务成功率、用户纠正次数、输入 token、发现调用次数和首个有效动作延迟；不预先承诺节省比例。
8. 用“先完成研究专属检查，再交付可编辑 PPTX”验证是否真需要 C；交接应保留来源与限制，确认不会携带对方服务凭据或扩大写入权限。

本次证据足以支持分阶段设计和 B 的优先级判断；不足以宣布任一产品的所有当前安装版本均通过上述实验，也不足以要求立即实现跨插件协作。

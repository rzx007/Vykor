# Codex 会话消息页样式调研与 Vykor 对照

> 状态：历史研究快照，记录 2026-10-13 的界面对照与改进建议。

日期：2026-10-13。依据：用户提供的 Codex 截图、随后提供的 Vykor 当前截图、实际安装包 CSS/JavaScript，以及当前 Desktop 源码。

## 1. 结论与优先级

Codex 的阅读体验主要来自可读的居中内容列、随字号变化的排版、正文与过程记录的视觉层级，以及技术内容的轻量处理。字体本身只是一部分。

我们当前已经有 **16px 正文、1.68 行高、约 712px 文本列和 16px 相邻段距**，不宜再把“整体放大字号”当成主要优化。对照截图与源码，优先处理：

1. **让行内代码的轻量样式实际生效。** 当前截图中的灰底约 `#DCDCDD`，频繁出现时像一串标签；已有轻背景 CSS 没有命中自定义组件。
2. **统一实际代码块与目标 CSS。** 自定义代码块仍有背景、边框、圆角、阴影和 44px 工具栏，另一套轻量 CSS 不作用于它。
3. **收敛已经完成的工具结果。** 普通工具行已经较轻，文件/终端结果卡仍占较多空间；默认摘要，详情可展开，更适合长会话。
4. **建立过程说明与最终回答的不同节奏。** 现有渲染器已传递 phase，但样式没有利用它。
5. **核对段落结构，再调宽度和间距。** 一段中的软换行不会产生相邻段落间距；不能仅凭密集文字截图断言现有 16px 段距没有生效。

本报告前 8 节与证据索引保存的是实施前的调研快照；后续 UI 调整记录见第 9、10 节。没有启动预览或操作用户界面。

## 3. 字体、字号与字重

| 项目 | Codex 安装包声明 | Vykor 当前源码 | 解读 |
| --- | --- | --- | --- |
| UI 字体 | 默认栈 `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` | `Inter Variable`，中文声明回退到 `Noto Sans SC`、微软雅黑等 | 默认栈与实际字形不是同一概念；中文具体回退未核实 |
| 正文专用字体 | `--font-content` 可独立配置，否则回退 UI 栈 | 助手正文沿用 `--font-sans` | 可以分开 UI/正文/代码，但不用先更换全部字体 |
| UI 基准字号 | 设置默认 14px，可修改 | 默认 14px，可选 12–18px | 两者 UI 基准并非巨大差异 |
| 聊天正文 | 默认继承 UI 字号；可由独立 chat override 修改 | UI 字号 + 2px，默认 16px | Vykor 正文已经更大，截图不证明 Codex正在使用默认 14px |
| 代码字号设置 | 默认 12px，聊天代码可独立 override | 运行期默认 Geist Mono 14px，可选 11–18px | 不应把 main.css 的初始 13px 当成最终偏好值 |
| 正文字重 | Electron body 声明 430；Markdown 内仍可能继承或覆盖 | 助手 Markdown 400，普通 body 450 | 字重的实际效果受字体是否支持该重量影响 |
| 强调文字 | `b,strong` 用 600 | strong 和标题用 600 | 避免整段加粗，优先强调短语和真正的小标题 |

依据：C01、C05、C22、C25、J01–J04；Vykor 的 [字体定义](../apps/desktop/src/renderer/src/components/appearance/appearance-fonts.ts)、[偏好](../apps/desktop/src/renderer/src/components/appearance/appearance-preferences.ts)、[应用偏好](../apps/desktop/src/renderer/src/components/appearance/appearance-provider.tsx)、[正文 CSS](../apps/desktop/src/renderer/src/assets/main.css)。

安装包虽然包含 OpenAI Sans 的 400/500/600 字体文件，但 JS 选择它需要主题配置或额外开关条件。**存在字体资源，不证明这张截图使用 OpenAI Sans。** 当前 Vykor 直接加载 Inter 与 Geist Mono；声明了 Noto Sans SC 的回退名，也不证明该字体已被加载。

建议保留现有 Inter 和代码字体，先核对中文回退与中英文混排。字号偏好最好明确区分“界面大小”“聊天阅读大小”“代码大小”，避免用户只想放大正文却同时改变侧栏密度。

| 窄窗口 | 通过内容容器条件与 padding 调整 | 内容列流式缩小；Composer 最大 760px，窄窗口减去左右留白 |

截图中的 Codex 正文从 x≈483 开始，阅读列大约 800–810 个图像像素；Vykor 表格和正文从 x≈87 到 x≈799，约 712 像素。这是截图中的几何观察，不能反推原始 CSS px 或唯一布局分支。48rem 在根字号 16px 的条件下为 768px，也不是所有窗口永远固定 768px。

我们的行高已经与 Codex 在相同 16px 字号时接近。若单纯为了接近 Codex，把 1.68 改成 1.625，实际只差不到 1px，收益远小于修复代码标签和工具卡片层级。

当前截图下半部多段内容比较密集，但 CSS 已有段距。需要检查文本是否用了真正的 Markdown 空行分段：同一 `<p>` 中的换行、连续说明与真正的 `<p> + <p>` 是不同情况。内容生成应保持短段落和明确分组；不宜自动按中文句号拆段，也不宜给所有软换行补大间距。

内容列可以保留当前默认值，提供更宽的阅读选项，让长表格、较多英文和代码的用户选择。避免为了加宽再缩小字号，也避免每种 Markdown 内容拥有不同的左对齐基线。

## 6. 行内代码、代码块、表格与工具记录

### 行内代码：目前最确定的改进点

Codex 的行内代码声明为 `0.92em`、圆角 6px、padding `1px 6px`，并使用轻表面混色；多行片段有 `box-decoration-break: clone`，可以在换行处保持背景和内边距。（C15–C17）

我们的 [自定义 inlineCode](../apps/desktop/src/renderer/src/components/desktop/conversation-page/message/markdown/streamdown-components.tsx) 第 37–41 行实际上使用：

```text
rounded-md bg-input/80 px-1.5 py-0.5 text-[0.87em]
```

它没有输出 `data-streamdown="inline-code"`，因此 [main.css](../apps/desktop/src/renderer/src/assets/main.css) 第 813–818 行已经写好的轻背景、0.9em 等规则命不中。本地 Streamdown 2.5.0 的自定义 wrapper 直接传原 props，标记只在默认 renderer 中添加；不能指望库替自定义组件补标记。

建议统一实际组件与 CSS 的作用目标，使用更轻的会话代码表面、约 0.9–0.92em 和较小的上下 padding。代码标识保持等宽字体，灰底仅帮助区分语义，不应成为每句话最显眼的部分。长路径允许断行，短标识保持清晰边界。

### 代码块：修实际组件，而不是只修改没命中的 CSS

Codex 的代码表面使用基础表面叠加轻色层，代码正文行高有 `max(1.5em, 20px)` 的声明。（C18、C19）本次没有观测实际展开的 Codex 代码块，不能只根据一条背景规则断言其全部外壳没有边框或阴影。

我们的 [Markdown fence 渲染入口](../apps/desktop/src/renderer/src/components/desktop/conversation-page/message/markdown/streamdown-renderers.tsx) 第 10 行替换为 [CodeBlock](../apps/desktop/src/renderer/src/components/ui/code-block.tsx)；后者第 230 行附近的实际外壳仍是圆角、边框、`bg-muted/40` 和 `shadow-sm`，工具栏高 44px。main.css 针对默认 `data-streamdown="code-block"` 的轻量规则没有命中这个自定义组件。

建议给实际 CodeBlock 增加会话阅读用途的轻量变体，控制背景、边框与阴影的叠加；工具栏可以更紧凑，保留语言、复制和键盘焦点。文件预览与差异审查仍按各自需求展示，不要因为改聊天代码块一起削弱其信息。

### 表格：现有基线已经比较接近

Codex 表格字体为 `max(代码字号, 正文字号×0.875)`；表头 600 字重、底部 1px 分隔线，单元格间留白根据正文缩放。（C20、C24）

我们截图中的表格已有浅表头、细横线和明确列对齐，不应重新包装成大卡片。主要关注：数值与标识的对齐、长内容断行、窄窗口横向滚动、动作按钮的可发现性。hover 与 focus 都应能访问操作，不能为了视觉干净把键盘用户的入口隐藏。

### 工具记录：普通行与成功卡片应有不同重量

Codex 截图中运行命令、文件编辑和代理完成记录主要是浅灰单行，图标与文字共同识别活动；普通记录与重要状态通过颜色、间距建立区别。源码有普通/分组间距 16px/4px 的 token，但完整活动行的实时计算高度本次未测。（C07）

我们普通工具行已经使用约 13px/28px 高、14px 图标和 8px 图文间距，适合保留。自家截图的“已编辑 3 个文件”卡片约 195 个图像像素高，文件路径占了三行独立区域；这是明显的空间差异。

建议已完成工具默认展示紧凑摘要，例如“已编辑 3 个文件”，点开再看文件列表、完整路径和详细输出；正在运行或失败时保留原因、操作和必要进展。不能统一折叠需要用户批准、错误处理或检查差异的结果，也不能以成功摘要代替实际检查结果。

## 7. 过程与结果的层级

我们的 [AssistantMarkdown](../apps/desktop/src/renderer/src/components/desktop/conversation-page/message/assistant-message.tsx) 第 316 行已输出 `data-phase="commentary" | "final_answer"`，目前两者使用相同排版。

可采用三层：

- **最终回答：**保留当前 16px 正文与正常前景，结论、短标题和重点短语清晰。
- **过程说明：**仍保持可读；用稍紧的块间距或明确的次要文字 token 表达阶段，不把重要解释变成低对比小字。
- **工具记录：**用已有紧凑单行，按需展开结果；完成后可聚合，失败和待批准保持清晰。

还需同时约束回答内容：避免每句都 bold、连续堆积代码标识、将所有日志写入正文。截图中同样是 600 字重，一两个重点短语能帮助扫描，整段加粗则会挤掉层级。

## 8. 建议实施顺序与验证范围

| 批次 | 改动 | 验证重点 |
| --- | --- | --- |
| 一 | 修行内代码/代码块实际样式来源 | 自定义 renderer 的标记或明确 class 与 CSS 对应；代码复制、长行、未结束 fence 和深浅主题保持可用 |
| 二 | 收敛已完成工具卡片，整理过程/结果节奏 | 运行中、完成、失败、待批准分别可理解；展开、键盘访问和文件打开不退化 |
| 三 | 核对段落结构与字体偏好，按需增加阅读列宽选项 | 中英文混排、真实多段落、软换行、列表、长表格及窄窗口；不要重复放大已足够的正文 |

这些调整优先复用现有组件，并遵循 [DESIGN.md](../apps/desktop/DESIGN.md) 的语义颜色、图标、层级、克制阴影和减少动态效果要求。当前没有新增组件选型需求；实际需要新交互组件时，再按项目约定评估 beUI。

按用户约定，接入 UI 后由用户查看样式并反馈，默认不主动搭建预览或截图。调研阶段只做静态样式核实；后续代码验证不能替代用户对实际视觉效果的反馈。

## 9. 第一轮实施记录

在用户确认开始后，落实以下调整：

- 自定义行内代码补齐样式标记，移除较重灰底与字号的重复定义，使用既有轻量会话 CSS；长标识允许换行。
- 为实际 CodeBlock 提供会话变体，作用到真实容器、工具栏和代码内容；文件预览继续使用默认变体，复制按钮保留清晰键盘焦点。
- 文件编辑结果改为默认收起的单行摘要，展开后可查看全部已记录文件；差异审阅入口保持可见，文件打开及行数统计规则保留。
- 已结束或已停止的终端采用紧凑摘要，命令详情按需展开，打开日志的入口保持可见；运行中、失败、不可用与查询错误继续展示原有必要信息。
- 助手内容单元间距调整为 16px；过程说明使用独立次要文字颜色，保留 16px 正文与 1.68 行高，不对容器整体降低透明度。

相关 4 个测试文件共 83 项测试通过，其中新增两项展开行为回归测试已先失败、后通过。Web 类型检查通过。终端组件的 `react-hooks/refs` 与 `react-hooks/set-state-in-effect` 两条 ESLint 报错已通过对 HEAD 原文件运行相同检查确认属于原有问题；本轮没有调整该生命周期逻辑。

样式没有通过截图或预览验证，仍由用户在实际应用中检查阅读节奏、灰底轻重和展开体验。

# 未知工具结果阻断默认关闭的原因

> 状态：当前决策记录（2026-10-28）。默认关闭跨操作阻断，后续设计待重新评估。

## 当前决定

默认关闭“某个工具结果不确定，就阻止整棵会话树继续执行其他写入”的行为，保留操作记录、权限检查和同一操作的重复执行保护。用户明确要求先恢复正常使用，留下原因文档，之后再决定是否重做这项能力。

这次不处理附件丢失或历史图片恢复；相关修复已撤回。

## 触发问题的实际经过

会话 `e373d417-d9b2-4d99-b681-25e90bf42c27` 中，浏览器导航到 `http://localhost:5173` 时返回 `ERR_ABORTED`。执行层把这类错误保存成 `unknown`，意思是无法确认实际影响。此后新的构建命令被旧记录拦截，即使构建与这次导航没有业务关系。

第一次阻塞来自 `operation_f0a08be6-dee3-4f46-8801-976fcb495091`。通过现有人工核对接口确认未生效后，该会话实际运行 `npm run build` 成功。后来浏览器导航再次失败，产生 `operation_38a07fc3-50da-468d-9a6b-ec55f48b6f42`，启动 `5180` 端口预览的 `TerminalOpen` 又被拦截。逐条清理旧记录无法解决反复发生的问题。

同时发现，读取或等待后台工作结果也会被当作可能写入的操作拦截。这会妨碍父代理等待子代理，或读取失败原因。相关修复只把可信的内置 `JobList`、`JobRead`、`JobWait`，以及内置 Browser 的 `inspect` 动作标为只读；同名替代工具和控制类动作不能借此获得放行。

## 原机制想解决什么

工具可能已经完成外部写入，但返回结果在超时、断连或进程退出时丢失。如果直接重试，可能重复付款、发消息或创建记录。因此系统在调用前保存操作和实际尝试，调用后保存结果；不确定时保留原记录，供可信宿主核对。

这个目的仍有价值。当前问题出在“不确定结果应该影响哪些后续操作”的决定过于宽泛。

## 为什么现在会妨碍使用

- 普通工具异常也可能被归为未知结果，浏览器导航失败因此变成全局执行障碍。
- 阻断范围覆盖父子会话整棵树，新的构建和终端操作会受到无关历史错误影响。
- 结果读取与等待没有完整声明为只读，连了解发生了什么的途径都可能被拦截。
- 恢复主要依赖人工核对接口，正常使用流程缺少足够清楚的恢复入口。
- 检查不止一处：Server 检查整棵会话树，存储层在实际派发时又检查同一会话。只关闭前者仍会阻塞。
- 真实 Browser 经 Node Agent 的额外工具入口注册，来源是 `agent`。只覆盖 `builtin` 的测试没有覆盖实际装配路径。

## 设置与实际执行流程

全局设置为：

```json
{
  "blockOnUnknownToolOutcome": false
}
```

缺省或 `false` 时，历史未知结果不再阻止其他操作；明确设为 `true` 才恢复这项阻断。设置经过现有读取、类型校验和持久保存入口，也支持现有 Config 设置命令。派发参数由宿主读取已校验的设置生成；普通工具不能仅在自身输入或结果元数据中附带同名字段来改变检查。

Daemon 创建 `ToolOperationService` 时传入设置读取函数。每次授权及派发重新读取当前值，因此设置更新后不必重建 Agent。Server 将最终布尔值传给存储层，两处检查使用同一个决定。直接使用底层 repository、未传此参数的调用方仍保留原来的严格检查。

入口与状态位置：

| 内容 | 位置 |
| --- | --- |
| 设置类型、默认值与文件校验 | `packages/host-config/src/settings/` |
| 在线修改设置与 Config 值转换 | `packages/server/src/application/default-services/configuration/settings-service.ts` |
| 将当前设置接入工具执行 | `packages/server/src/application/daemon-application.ts` |
| 会话树检查与派发参数 | `packages/server/src/application/session/execution/tool-operation-service.ts` |
| 操作、尝试与结果持久记录 | `packages/services/src/tool-operations/tool-operation-repository.ts`，共享 SessionStore 和 SQLite |

旧版后台必须先加载新代码；只修改配置文件不能让旧实现获得此行为。

## 仍保留的约束

关闭跨操作阻断不会删除或改写旧的未知记录，也不会把失败伪装成成功。原始尝试、错误和核对证据继续保存。

每次新调用仍经过工具权限、强制规则、原有审批和派发前校验。会话归属、当前写入者、运行状态、规则版本和操作修订仍需匹配。同一个未知操作不能因此自动重放；需要新的操作仍按原流程授权。

已经调用工具、却无法保存结果的存储故障，仍在当前进程中阻止继续派发其他危险操作，直到对应记录得到确定结算或可信核对。这属于回执无法保存的保护，不跟随本开关关闭。进程重启后，恢复出的未知记录按当前开关处理。

工具实际调用尚未结束时，人工核对仍不能强行确认已生效或未生效。插件应用内部自己的去重和操作状态也不由本开关控制。

## 本次验证范围

- 默认值、显式启用和关闭、非法设置值，以及在线设置更新。
- 使用真实 Daemon、Node Agent 和临时 SQLite，先触发浏览器异常，再运行真实 Shell 写入：默认可继续、显式启用会拦截，普通权限拒绝仍然生效。
- 开启阻断时，真实后台工作的读取与等待可完成，控制动作、写入和同名替代实现仍被阻止。
- 已有未知记录及其尝试保留，原有人工核对和调用中保护继续测试。
- 实际构建产物验证可信工具身份，避免源码测试通过但打包后声明失效。

自动化用例在对应包的 `__test__/` 和跨包的 `tests/agent-integration/__test__/` 中；运行结果以本次提交前实际验证为准。

## 后续重新设计时需要回答的问题

需要区分“明确失败”和“可能已生效”，明确哪些工具值得阻断、阻断哪些相关操作，并提供用户能理解的状态说明与恢复入口。还需要覆盖父子会话、重启恢复、迟到结果和真实工具装配路径。

这些问题暂不在本次改动中扩展实现。当前先恢复可用性，保留记录和回放保护，便于之后根据实际案例作决定。

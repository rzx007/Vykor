## 目标与范围

网络短暂波动时，任务应进入可见、可取消的重试过程，恢复后继续当前模型调用。只有遇到不可重试错误或用完重试预算，才结束运行并说明原因。

覆盖请求发出失败、流式输出中断和长时间无数据。不自动重新执行整项任务，不重跑已经完成的工具，不包含进程重启后的任务恢复。

需要区分两段连接：客户端到后端的连接负责显示任务事件；后端到模型服务的连接负责生成内容。前者重连成功，不代表后者已经恢复。

## Codex 官方文档确认的机制

来源：[Codex Configuration Reference](https://developers.openai.com/codex/config-reference/)，查阅日期为 2026-09-25。

| 配置 | 作用 | 文档默认值 |
|---|---|---|
| `model_providers.<id>.request_max_retries` | HTTP 请求失败的重试次数 | 4 |
| `model_providers.<id>.stream_max_retries` | SSE 流中断的重试次数；SSE 是服务端持续推送数据的连接 | 5 |
| `model_providers.<id>.stream_idle_timeout_ms` | 流连续没有数据时的超时时间 | 300000 毫秒，即 5 分钟 |

可借鉴的是：请求失败与输出中断分开处理，等待数据也有超时限制。这些配置不等于所有内置提供商都能被同名配置覆盖。

官方配置文档不能证明重试时如何处理残缺文字、工具调用、服务端续传或具体等待算法。下文是本项目建议，不是对 Codex 内部实现的描述。

## 改造前的缺口（2026-09-25）

本节保留最初调研的故障背景，不表示当前实现仍有这些缺口。实现后的验证和整体审核见[收尾记录](./superpowers/plans/2026-09-26-model-network-retry-verification.md)。

### 1. 应用层主要按 HTTP 状态码重试

[OpenAI 适配器](../packages/api/src/providers/openai.ts)、[Anthropic 适配器](../packages/api/src/providers/anthropic.ts) 和 [Codex 适配器](../packages/api/src/providers/codex.ts) 都有重试循环，但进入重试要求错误存在 `status` 或 `statusCode`，且命中各自的状态码集合。

连接重置、连接超时、流读取失败等错误可能没有 HTTP 状态码，因此会绕过该重试分支。OpenAI 和 Anthropic 的底层 SDK 可能还有独立重试；不能据此宣称整个调用链完全没有网络重试，但当前应用层确实没有完整覆盖流中断。

三个适配器的状态码集合也不一致，例如 Codex 包含 504，OpenAI 当前集合不包含 504。

### 2. Codex 适配器没有验证完整结束

`streamOnce` 处理了 `response.completed`，但没有记录并强制检查该事件是否出现。读取流结束后，会继续发出工具调用、usage 和 `complete`。

如果连接提前结束且读取器没有抛错，就可能把不完整输出当成正常完成。修复时必须区分正常结束、服务端明确失败和未完成就断流。

### 3. 重试后的输出缺少替换边界

[QueryEngine](../packages/core/src/engine/query-engine.ts) 一边转发事件，一边把文字追加到 `assistantText`。适配器内部重新请求，并不会自动撤回已经交给引擎和界面的文字。

只扩大可重试错误集合，可能让第一次残缺文字与第二次完整文字拼接在一起。思考内容、工具调用和 token 用量也需要明确归属，不能只清空适配器的局部变量。

当前引擎在本次流遍历结束后执行收集到的工具调用。这个边界应保留，并要求模型响应确认完整后才允许执行工具。

### 4. 重试过程不可见，取消支持不一致

模型适配器的重试分支没有发出包含次数和等待时间的专用状态。用户无法区分正在等待重试与任务卡住。

OpenAI 和 Anthropic 使用 [abortableDelay](../packages/api/src/providers/retry.ts)，等待期间可取消；Codex 适配器仍使用普通 `setTimeout`，不能立即中断等待。

### 5. 客户端重连已有实现

[客户端事件同步](../packages/client/src/state/sync.ts) 已有重连、事件序号恢复和重新获取状态的流程。应复用这条显示状态的通路，不另建一套客户端重连系统。

[core 中的 retryWithBackoff](../packages/core/src/utils/retry.ts) 虽然识别部分网络错误码，但上述三个模型适配器未使用它；函数存在不代表实际请求受到保护。

以上是改造前静态代码确认的缺口。用户最初那次故障究竟来自哪段连接、什么错误，仍需结合当时日志确认；本轮使用可控故障验证恢复行为。

## 建议的运行流程

1. 引擎以已确认的消息历史发起当前模型调用，为本次生成标识独立的尝试。
2. 适配器读取流，输出暂存于该尝试；界面可以实时显示，但不能把残缺工具参数当成可执行指令。
3. 网络错误或提前断流发生时，保留原始错误，判断是否可重试，以及剩余次数、总等待预算。
4. 可重试时，保持原任务进行中，发布重试次数、原因和下次尝试时间；等待期间响应停止操作。
5. 下一次尝试开始前，将上一轮残缺输出标为已被替代，并重置当前生成的文本、思考内容和待执行工具集合。此前完成的消息和工具结果保留。
6. 使用同一份已确认输入重新请求当前模型响应。除非提供商明确支持续传，否则不声称从上一个 token 接着生成。
7. 收到协议规定的结束信息后，区分正常完成、长度受限结束与网络断流。长度受限结束保留可用文本、追加一次截断提示，不进行网络重试；最终对外 complete 必须在这些内容之后发出，再提交本次生成。有完整有效工具调用时，按原工具规则执行，不能执行截断参数。
8. 不可重试或预算耗尽时，结束运行，保留错误摘要和尝试记录。迟到事件不得把已结束或已取消任务恢复成运行中。

重试协调应有一个明确的负责人：建议由引擎掌握输出替换与次数预算，适配器负责识别协议完成状态和提供结构化错误。实施时审查并收敛现有适配器循环及 SDK 重试，避免多层循环把请求次数相乘。

## 错误与等待策略

| 情况 | 建议处理 |
|---|---|
| 连接重置、临时 DNS 故障、连接或读取超时 | 在预算内重试，检查错误本身及 `cause` 中的原因 |
| 429 临时限流 | 按服务端等待提示重试；余额或额度耗尽不能简单等同于临时限流 |
| 500、502、503、504，以及提供商明确规定的临时过载 | 有界重试 |
| 流未收到完成标记就结束 | 视为中断，进入当前生成的恢复流程 |
| 用户主动取消 | 立即结束等待或请求，不重试 |
| 401、403、无效参数、不支持的模型能力 | 直接报告需处理的问题 |
| 未知编程错误、解析错误 | 不用兜底无限重试掩盖问题，保留诊断信息 |

建议起点是指数增加等待时间，例如 1、2、4、8 秒，再加少量随机延迟，避免多个请求同时重试。次数、最大等待和总时限应明确；具体默认值在实施时结合产品体验确定，Codex 默认值仅供参考。

`Retry-After` 应支持秒数和 HTTP 日期。若服务端要求的等待超过剩余总预算，应明确结束或提示，不能把它压短后提前重试。

流空闲超时指连续没有收到数据，不是整段生成总时长。服务端心跳与有效输出需要分别考虑，避免把模型正常长思考误判为断线。

## 状态保存与界面

建议的职责分工：

- 适配器：提供错误类型、状态码、等待提示、请求标识和是否收到完成事件；保留原始原因。
- 引擎：保存当前模型调用的尝试次数、截止时间、取消信号和未完成输出；决定何时重试、替换或提交。
- 运行记录与事件通路：保存可供诊断的尝试结果，将当前重试状态纳入客户端可恢复的状态。先检查现有 Run/Attempt 模型，不能直接假设“一次 HTTP 请求”等于“一次运行 Attempt”。
- 客户端：显示重试过程，并依据明确的生成标识替换残缺输出；刷新或重连后仍能恢复当前状态。

建议文案：

> 连接中断，2 秒后重试（第 2/5 次）。

恢复成功后清除等待状态并继续显示内容。耗尽预算后显示最终原因，并允许用户手动继续。手动继续的恢复边界需明确，不能隐式重跑已完成工具。

诊断记录包含提供商、模型、错误类型、HTTP 状态码、重试次数、等待时间、是否已有输出，以及可获得的请求标识。不记录密钥或完整敏感请求正文。失败尝试的用量如不可得，应标为未知，不能假定为零。

执行计划审核后补充以下约束：

- 过滤失效输出不仅发生在界面。服务端从数据库重建模型历史、提取公开回复时也必须排除被替代内容；新格式中未确认提交的残缺输出不能作为已完成历史送回模型。
- 关闭适配器和 SDK 重试时，压缩和记忆提取必须接入独立、有界的重试。辅助调用先缓冲本次输出，成功后交付，避免摘要或记忆 JSON 拼接失败前缀；记忆写入不放进重试循环。
- 每次请求记录用量为完整、部分已知或未知。未知时不填零；汇总只累加已知消耗并保留“不完整”标记，刷新后仍能展示“已知用量，部分请求用量未知”。具体事件、字段和去重规则见执行计划。

2026-09-26 核对新增功能后，执行时还必须保留以下行为：

- 模型输出上限已由请求配置中的 `maxOutputTokens` 传入 API 的 `maxTokens`，压缩通过 `setOutputReserve` 预留对应空间。同一次生成的所有重试固定使用同一上限、reasoningEffort 和已压缩输入；网络重试不再次压缩或重读配置，下一正常回合再采用配置变化。
- `length`/`max_tokens` 属于明确的长度受限结束，不等同于提前 EOF。输出顺序为正文、必要的截断提示、最终 complete；持久提交须覆盖提示，重载后不能消失或重复。Codex 的 `response.incomplete` 须按具体原因分类，不能与所有网络错误混为一谈。
- Desktop 已合并短时间内的会话更新，仅发送窗口内最新完整快照。输出失效、重试状态及用量完整性必须能由最新快照恢复，不能要求窗口逐个收到生成事件；沿用更新合并，不为显示重试而恢复逐 token 全量 IPC。

## 建议实施顺序

1. 统一可重试错误识别和可取消等待，保留提供商差异；审查底层 SDK 重试次数。
2. 为各协议加入完整结束校验，特别是 Codex 的 `response.completed`。
3. 接通引擎的尝试边界、残缺输出替换与工具执行保护。
4. 通过现有事件和状态同步链路展示重试过程，再启用完整的中途恢复能力。

优先扩展现有文件，不新增重试依赖。不应在第 3、4 步完成前，把所有中途错误直接改成透明重发，否则会引入重复内容和状态不一致。

## 验收场景

默认策略：请求错误最多重试 3 次、流中断最多重试 3 次，同时总重试最多 5 次（首次请求不计）。从首次可重试失败开始计算 180 秒恢复窗口；连接阶段 60 秒超时，流空闲 300 秒超时，恢复窗口开始后以更早的截止时间为准。恢复中的持续输出不会延长窗口，长度受限结束不重试。

SDK 路径按可观察的协议事件刷新空闲时间；无法观察的底层 SSE 注释心跳不作支持承诺。重新发起模型请求可能产生额外费用，未知用量会明确标记。CLI 终端已打印文字不可撤回；JSON 最终结果与 Desktop/TUI 使用有效输出。协议版本 5 要求客户端和服务端同步升级。

| 场景 | 预期结果 |
|---|---|
| 首次请求连接重置，第二次成功 | 自动重试并成功，只产生一份最终回答 |
| 输出一半后读取失败 | 显示重试状态，残缺输出被替换，不拼接重复文字 |
| 流正常关闭但缺失协议完成标记 | 不报告成功，不执行残缺响应中的工具 |
| 工具参数输出到一半断线 | 不执行不完整工具调用 |
| 前一次模型调用已执行工具，下一次调用断线 | 保留已有工具结果，只重试当前模型调用 |
| 429 带秒数或日期形式的 Retry-After | 遵守等待要求及总预算 |
| 401、403、参数错误、额度耗尽 | 给出对应问题，不进入盲目重试 |
| 等待期间点击停止 | 立即取消，不发出下一次请求 |
| 一直断网 | 到达次数或时间上限后明确失败 |
| 长时间没有流数据 | 触发空闲超时；正常心跳和长思考行为按协议处理 |
| 重试期间界面刷新或重连 | 恢复当前重试状态，不重复追加旧事件 |
| 长度受限结束 | 不网络重试，提示一次，最终提交包含提示，重载一致 |
| 重试期间修改输出上限 | 当前生成仍使用原上限和输入，下一正常回合采用新值 |
| Desktop 同一合并窗口内经历失效、重试、成功 | 最新快照无重复文字或残留等待提示 |
| 底层 SDK 重试关闭后主生成及辅助调用 | 各自有界恢复，实际请求次数无多层放大 |

实现时优先用模拟连接错误、截断流和可控时钟验证这些边界，不依赖真实断网或真实模型计费。本文不代表功能已经完成或测试已经通过。

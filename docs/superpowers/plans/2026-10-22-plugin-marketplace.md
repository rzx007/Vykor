# GitHub 插件市场分阶段方案

> 状态：当前实施方案；发布源、桌面市场和自定义源已实现，验收记录见文末。
> 日期：2026-10-22。

## 推荐方向

建立公开仓库 `rzx007/vykor-plugins`，用 GitHub Pages 提供市场目录，用 GitHub Releases 提供构建好的 ZIP。客户端只下载、校验和安装，不在用户机器上编译插件或执行依赖安装。

市场是现有插件安装机制前面的发现与分发入口。安装后仍进入同一份 Native Plugin 安装记录、权限校验、执行链路和右侧应用面板，不产生另一种插件运行方式。

首期收录 Excalidraw、Text Inspector、Notes。源码仍以 Vykor 当前仓库为准，发布仓库按固定提交提取、构建，避免维护两份源码。本方案首批构建基线为 `rzx007/Vykor@3d7945e3b674e9f39606df5c1cf2488bc7f17b6e`；后续升级通过 PR 修改固定提交。

## 调研依据

### ZCode 可以借鉴什么

本地调研目录为 `D:/code/personal-project/zcode-plugins`，提交为 `ded80218a414bfe20935ae88e467ec0448e98de2`。

- 根目录 `marketplace.json` 是唯一收录清单，当前包含 46 个插件。条目指向仓库内的插件目录，提供名称、版本、分类和展示信息。
- `scripts/plugin-catalog.mjs` 校验条目、清单和构建版本是否一致；通用构建脚本不硬编码插件名称。
- `scripts/build_dist.py` 生成固定版本路径下的 ZIP，再生成包含下载地址、SHA-256、大小的发布目录。ZIP 固定排序和时间戳，便于检测同版本内容变化。
- `.github/workflows/publish.yml` 先构建、测试和校验，再部署静态分发文件。
- `dist/local-marketplace` 支持本地测试，但不会自行安装或启用插件。

采用这些分工和发布检查，不照搬 ZCode 的清单格式、宿主扩展、付费功能或整套构建系统。ZCode README 中的部分版本已落后于实际清单，市场展示应从清单和构建结果生成，避免手工维护第二份版本列表。

### 我们已经具备什么

| 现有位置 | 可以复用的能力 | 市场需要补的部分 |
| --- | --- | --- |
| `packages/plugin-sources/src/sources/local-zip.ts` | ZIP/TAR 解压、安全路径检查、100 MiB 压缩包与 250 MiB 解压上限 | HTTPS 下载、市场目录解析、下载内容校验 |
| `packages/plugin-sources/src/sources/git-source.ts` | Git 固定提交、来源摘要 | 保留给开发安装；当前只认仓库根目录，不作为市场安装主路径 |
| `packages/server/src/application/default-services/plugin-service.ts` | 预览实际清单、权限确认、拒绝替换受管理插件 | 从市场选择版本、记录来源、安装和更新的统一结果 |
| `packages/plugins/src/installation/installer.ts` 与 `store.ts` | 内容摘要、不可变代码快照、原子更新安装记录 | 可选市场来源信息、有界安装回执，限制跨源替换 |
| Desktop 插件页与 Main 的 `selection-store.ts` | 已安装列表、详情、权限弹窗、短期选择凭据 | 浏览市场、更新状态、市场选择凭据 |

现有 `InstalledPluginRecord.origin` 表示原生或转换格式，不表示下载来源；不能用它代替市场来源记录。现有安装回包主要是 `message`，不能把它当成已经持久化的市场安装回执。

## 仓库和发布职责

拟创建仓库 `rzx007/vykor-plugins`，默认分支 `main`，公开可读。2026-10-22 的只读核对确认：本机 GitHub CLI 已登录 `rzx007`，对 Vykor 有管理权限；查询拟建仓库返回 404，尚未创建。新仓库的 Pages 和发布设置需要在创建后开启，当前没有宣称它们已经可用。

仓库内容限定为：

- `marketplace.json`：作者维护的收录清单。每个条目声明构建来源、相对目录和分类；发布版本、名称、描述、作者等从实际插件清单读取。
- `scripts/`：校验收录、从固定提交提取源码、构建、确定性打包、生成发布目录。全部使用现有 Node.js 技术栈。
- `schemas/`：发布目录格式及测试样例，与宿主同一版本的格式规则保持契约测试。
- `.github/workflows/validate.yml`、`publish.yml`：分别执行只读校验和正式发布。
- `README.md`、`CONTRIBUTING.md`、许可说明：安装入口、收录流程、来源和许可责任。

首期插件来源固定为当前仓库的 `plugins/excalidraw`、`examples/plugins/text-inspector`、`examples/plugins/notes-app`。后续正式插件统一放在 Vykor 源码仓库的 `plugins/` 下，发布仓库只固定源码提交，不复制源码。2026-10-23 起 Excalidraw 已迁到正式目录，研究与写作、办公文档也改为市场分发；原有示例继续留在 `examples/plugins/`。

当前 Text Inspector、Notes 没有独立 LICENSE，Vykor 根目录也没有可直接继承的 LICENSE。建议这两个自有示例及新仓库自有脚本采用 MIT，在首次公开分发前补齐文件和清单许可字段；两个插件分别递增至 `1.2.2`、`1.0.2`，并将发布源锁定到包含这些修改的实际提交。Excalidraw 保留现有 MIT 和第三方完整声明，不统一改写上游许可。

发布目录地址拟为 `https://rzx007.github.io/vykor-plugins/marketplace.json`，属于创建并部署成功后才生效的地址。Pages 只承载目录、图标与简短说明；大安装包和历史版本放 Releases，避免每次更新目录都重新上传全部历史包。

每个插件独立版本，发布 tag 使用 `<name>-v<version>`，ZIP 使用 `<name>-<version>.zip`。保留旧 Releases；已发布的同一插件版本不能更换文件。开启 GitHub 的不可变发布，先创建草稿、上传全部资源、发布成功，最后更新 Pages 目录。目录部署失败可单独重跑，不重建或覆盖已发布 ZIP。

## 发布目录约定

作者清单是构建输入，Pages 上同名文件是生成的分发输出，二者不靠手工同步。

| 发布字段 | 规则 |
| --- | --- |
| `schemaVersion`、市场 `id`、名称、维护者 | 格式版本固定为 1；市场 ID 不作为信任凭证 |
| `plugins[].id/name/version` | 必须与 ZIP 内 `.vykor-plugin/plugin.json` 一致；版本使用语义化版本，正式目录首期只收录稳定版 |
| 展示信息 | 描述、作者、许可、关键词来自插件清单；分类由收录条目声明；缺失信息不编造 |
| `componentTypes` | 根据构建后清单生成，支持技能、工具、MCP、应用等标记；不授予执行权限 |
| `artifact.url/sha256/size` | 指向固定 tag 的 HTTPS ZIP，SHA-256 校验实际下载字节；不能使用 `latest` 下载链接 |
| `requires.host/node/platforms` | 记录实际验收的宿主版本范围、Node 版本范围和平台；服务端在预览及安装时再次检查 |
| `source.repository/commit/path` | 公开可追溯的固定源码来源，不是客户端要执行的安装脚本 |

首期保持现有 ID：`dev.vykor.excalidraw`、`example.text-inspector`、`example.notes-app`，不为市场展示重命名。基线版本分别为 `1.0.0`、`1.2.1`、`1.0.1`；若改变实际分发内容，按版本规则递增。Excalidraw 明确要求运行插件服务的 Node.js 至少为 24。

首期发布包沿用现有样例包的文件布局，排除 `node_modules`、`.git` 和运行时用户数据；不同时进行包结构瘦身。清单声明的服务入口、页面及离线字体必须全部包含，安装后不能依赖作者源码目录。

## 用户看到的流程

在现有“插件”页增加“浏览市场 / 已安装”视图，复用当前搜索框、卡片、详情与权限弹窗。技能和 MCP 顶层页签保持现有分工。

浏览市场时显示真实条目、分类、作者、版本、能力标记及当前安装状态。进入详情后可安装；已安装版本有新版时显示“更新”。首次安装有权限要求时确认一次；同来源、权限没有增加的更新无需重复确认原权限。安装成功后给出“在新对话中使用”的入口，不自动向聊天发送消息。

权限来自下载后实际清单，市场宣传信息不能替代权限预览。`pluginData:write` 仍只授权声明过的应用专用工具保存自身数据，工作区导出仍逐次按原流程检查。市场安装不授予对话权限、额外文件权限或跨插件调用能力。

插件应用继续只在右侧固定面板展示，聊天保留具名入口，工作摘要继续聚合已有应用和任务。市场是管理页功能，不再增加面板起始页入口或聊天内嵌 UI。

## 安装、来源和回执必须一起打通

```text
发布仓库固定源码 → Actions 构建与校验 → Releases ZIP + Pages 目录
                                                       ↓
Desktop 市场页 → Main 持有选择凭据 → Server 下载并固定候选包
                                       ↓
                    实际清单与权限预览 → 用户确认所需权限
                                       ↓
              原 Native Installer → installed.json + 代码快照
                                       ↓
                         新会话使用 → 原工具权限与操作回执
```

1. 刷新目录由宿主完成，Renderer 只拿展示数据，不直接下载、解压或传递可信下载地址。目录缓存放在 `getPluginSourcesDir()` 下，按来源区分；来源设置为用户级，与安装作用域一致。
2. 服务端从已登记来源选择 `(sourceId, pluginId, version)`，流式下载，核对大小与 SHA-256，再复用现有归档安全检查和 Native 校验。目录最多 2 MiB，下载沿用现有 100 MiB 压缩包上限，设置超时和取消，不把内容一次全部读进内存。
3. 下载只接受 HTTPS。校验每次重定向，拒绝回环、内网和非 HTTPS 目标；官方源还限制仓库路径及 GitHub 正常资源下载域名。自定义源的资源须位于声明的同源地址；不隐式转向陌生镜像。
4. 预览固定目录摘要、下载摘要、插件身份、请求权限和兼容要求。Server 保存短期候选包，Main 保存绑定当前窗口、工作区和候选包的不可伪造选择凭据。确认不能换 URL、换包或只按同名插件再次解析最新版本。候选过期、来源被停用或移除时拒绝确认；候选文件变化时重新预览。
5. 安装记录增加可选 `provenance`：来源配置身份、目录地址、实际版本、归档摘要及固定源码信息。旧记录不强制迁移。官方标记由内置来源配置决定，不相信远端 JSON 自称官方。
6. 相同插件 ID 的更新只允许沿已绑定来源进行。同 ID 出现在多个源时分开显示，不能按名称合并或静默覆盖。换源、覆盖本地链接插件或接管无来源安装时必须明确确认；不因权限字符串相同就自动继承信任。受管理插件继续拒绝覆盖。
7. 旧 ZIP 安装可在确认身份、权限及完整内容摘要均一致后，明确选择“关联此来源”，只补来源信息而不重装。摘要不一致时走完整替换预览，不自行判断“同版本就是同内容”。
8. 每次安装/更新生成 `operationId`，绑定固定来源、插件、版本和归档摘要。在 `installed.json` 增加可选 `installOperations`，记录接纳及最终结果；成功回执与安装指针、来源在同一次原子写入中提交，不能只在插件记录里保留最后一个操作。终态保留 7 天、最多 1000 条，过期查询明确返回未知，不能据此重新执行。相同操作只执行一次；进程中断后未结算的操作先核对安装记录，无法证明结果时保持未知，不换 ID 自动重装。不引入新的通用任务框架或回执数据库。
9. 同一宿主内全部安装入口共用服务端的安装写入串行约束，保证两个插件同时安装不会因 `installed.json` 的读后写相互覆盖。它只约束安装记录写入，不关闭会话或中断应用；不能依赖 Renderer 按钮锁保护状态。
10. 更新失败保持原安装指针、启用状态和数据。已打开的应用继续使用捕获的旧代码快照，不自动关闭、重挂载或重载；新安装在新会话生效。需要立即使用新版时提醒先处理草稿，再由用户关闭旧面板并重新打开。

SHA-256 证明包与已获取目录一致，不独立证明作者身份。首期信任边界是内置官方来源、用户明确添加的来源和受控发布权限；不声称已具备独立签名验证。

## 分阶段交付

### 阶段一：做通可发布、可下载的官方源

- 创建公开仓库，启用 Pages、不可变 Releases 和发布环境保护；只在主分支或维护者批准的发布流程中授予写权限。
- 建立唯一收录清单，固定首批三个插件的 Vykor 提交；按各插件锁文件安装构建依赖，再执行已有构建、类型与必要测试。Excalidraw 沿用 README 的 `npm ci --ignore-scripts --legacy-peer-deps`，另外两个沿用各自锁文件构建。
- 新发布脚本采用固定文件顺序、时间戳及权限，校验两个独立打包结果相同。与当前 `package-example-plugins.mjs` 只适合样例打包的职责分开；不把当前带实时 ZIP 时间戳的输出直接当成可复现发布。
- 校验 ZIP 中所有入口、离线资源和许可；同一已发布版本若对应不同摘要，发布失败，不覆盖。
- PR 校验不使用发布凭据；运行插件构建脚本的 job 只有读权限，发布 job 只处理已验证制品。先发布 ZIP，再部署包含它的目录；失败继续保留旧目录。
- 交付验收：从公开 Release 下载三个 ZIP，通过当前桌面的“导入插件包”即可使用。即使停止后续阶段，本阶段仍提供真正可用的插件分发。

### 阶段二：桌面浏览、安装和手动更新

- 内置唯一官方源，增加市场列表、详情及安装/更新按钮；目录和下载缓存归 Server 管理。
- 在 `@vykor/plugin-contracts` 定义目录数据格式，在 `@vykor/plugin-sources` 实现读取、下载和候选包处理；后者不修改安装状态或决定权限。
- Server 增加 `/plugins/marketplace/catalog`、`/preview`、`/install` 和 `/operations/:operationId` 接口，路径均使用 `/plugins/marketplace` 前缀。Client、Main、IPC 和 Renderer 使用同一套输入输出约定。
- Server 的安装协调层组合候选包与原 Installer，完成上述来源绑定、权限复核、结果查询和失败保留规则；普通 ZIP/Git 入口也须识别已绑定来源，防止绕过换源提示。
- `InstalledPluginRecord` 只增加可选来源信息；安装存储顶层增加可选的有界操作回执，保留旧记录可读，不重写插件自己的画板、Notes 或草稿数据。
- “更新”仍是用户主动点击；不后台换代码、不自动刷新已打开的应用。
- 交付验收：干净用户配置可以浏览官方市场，安装 Excalidraw，正常绘图并自动保存；已有三个样例安装能安全关联或明确替换；更新失败和手动取消均保留原安装与草稿。

### 阶段三：自定义源和更新提示

- 在插件页“添加”菜单增加“添加插件源”，输入 HTTPS 目录地址，预览来源后登记。允许停用、移除和手动刷新，移除来源不卸载已安装插件或删除数据。
- 来源规范化地址作为配置身份的一部分；改地址属于换源，不复用原选择凭据。多个源不能靠相同远端市场名称取得相同身份。
- 进入插件页时执行一次有界更新检查，目录缓存 15 分钟，用户刷新可跳过缓存；只提示，不自动安装。离线显示已有缓存及更新时间，不显示虚构版本或空分类。
- 固化贡献 PR 规则：清单版本、真实构建、完整许可、普通工具与应用工具边界、独立安装包验证。
- 交付验收：两个源收录同一 ID 不会相互覆盖；停用来源会撤销待确认安装；来源不可用不影响已安装插件运行。

每阶段独立可合并和交付。涉及两个仓库、超过 8 个文件，主要改动覆盖插件契约、来源解析、安装协调、Client 和 Desktop；不增加服务器、数据库或第三方账号体系。

## 必要验证与验收

按阶段运行定向测试，不重复全量测试：

- 发布源：清单重复 ID、版本不符、构建入口缺失、许可证缺失、同版本改包、确定性 ZIP、目录部署失败和重复发布。
- 下载：SHA 错误、虚假大小、流超限、超时、重定向、私网目标、解压越界、压缩炸弹，均不能改变安装记录。
- 安装：候选过期、权限新增或撤销、换源、旧记录关联、并发安装、受管理冲突、断线后查询原操作；所有入口使用一致判定。
- 应用：更新前保留一份 Excalidraw/Notes 草稿，切换和收起仍能恢复；旧面板不被升级强制重挂载；新版只在重新打开后的对应运行实例生效。
- 权限与工具回执：自动保存仍等待服务确认；导出与覆盖工作区文件仍需原权限确认；模型调用不能取得应用自动保存授权。
- UI：复用项目设计组件，检查键盘和类型；外观由用户体验后反馈，不额外搭预览或截图。

宿主使用现有命令：`pnpm --filter @vykor/plugin-sources test`、`pnpm --filter @vykor/plugins test`、Server 相关 Vitest 文件、Desktop 新增市场组件与 Main 的定向 Vitest 文件；完成后执行受影响包的类型检查及 `pnpm check-docs`。只有改动实际影响应用挂载或执行链路时，追加既有 Electron 定向回归。

首期不做评分、下载统计、付费、私有仓库登录、自动依赖安装、Agent 自动安装或自动更新。ZCode 其余插件按需逐个适配和发布，不把第三方格式兼容、金融服务和特殊运行时混入市场首期。

## 失败处理和外部条件

- GitHub 或 Pages 不可用：已有安装照常运行，目录保留上次成功缓存；安装失败可继续使用当前 ZIP 导入入口。首期不引入未经验证的镜像或自动代理。
- 发布错误：恢复上一份目录或暂时下架条目，不篡改已发布版本。已安装错误版本由用户禁用；不自动回退代码并假设插件数据格式也能回退。
- 更新失败：旧快照与数据保留；不会为了修复下载而清空草稿或插件数据目录。
- 规模增长：目录仍只描述可安装版本，大包和历史版本留在 Releases；无需客户端 clone 整个仓库。
- 账号需求：维护者使用现有 GitHub 账号创建和维护公开仓库；Actions 使用仓库内置 `GITHUB_TOKEN` 及 Pages 部署权限；普通用户不需要 GitHub 登录、PAT、npm 或 Git。

最关键的假设是目标用户能访问 GitHub Pages 和 Release 下载地址。若实测不成立，再增加受控镜像，复用相同 ZIP 摘要和来源身份；不能静默切换到另一个发布者。

## 官方依据

- [GitHub Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)：公开仓库可使用 Pages；部署 job 需要明确权限与部署依赖。
- [GitHub 不可变发布](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)：正式发布后保护 tag 和附件；建议先草稿上传完整资源再发布。
- [ZCode 分发约定](https://github.com/zai-org/zcode-plugins/blob/ded80218a414bfe20935ae88e467ec0448e98de2/docs/distribution_CN.md)：本方案对其本地源码进行调研，借鉴目录、ZIP 摘要和版本不变规则。

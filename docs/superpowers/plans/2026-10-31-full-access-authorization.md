# 完全访问权限统一审批入口实现计划

> **面向 AI 代理的工作者：** 按任务分工实现并独立审查，使用失败测试、最小实现和实际运行验证。

**目标：** 主聊天、目标续跑和继承权限的子任务，在完全访问模式下不因普通工具或工具内部权限请求等待人工批准。

**方案：** 所有权限判断先执行禁止规则，再在 `PermissionChecker.checkTool()` 的唯一出口应用授权模式。工具内部的具体操作确认通过同一个权限检查器处理；普通模式保留单独确认，完全访问直接批准。持久审批中介只保存和等待真正需要批准的请求，不在中介里跳过禁止规则。

**边界：** 保留计划限制、工具和路径禁止、已识别命令禁止、运行绑定与取消检查。`AskUser` 仍可提出真正的问题；外部 OAuth 仍由用户完成；显式缩窄的子任务不会升级权限。

## 任务一：统一权限决定与工具内部请求

修改 `packages/agent-contracts/src/policy/permissions.ts`，为检查方法增加可选的具体操作确认上下文。

修改 `packages/permissions/src/index.ts`：私有方法只检查规则，公共入口统一处理完全访问和强制确认，不再在 Shell 分支补充完全访问特例。

修改 `packages/core/src/engine/tools/tool-execution-context.ts` 和 `packages/core/src/engine/query-engine.ts`：将内部 `requestPermission` 接入当前检查器，使用当前运行捕获的工具定义取得来源和参数定义。未知目标拒绝，禁止结果拒绝，允许结果直接批准，确认结果交给原宿主；取消后不能批准。不接受工具自报的来源作为证据。

## 后续回归复查

F01 新增的 Shell 分析曾在分析不完整时直接返回 `ask`，覆盖了完全访问原本的允许结果；不是目标续跑遗失了权限。给定目标会话的只读记录确认审批模式为完全访问、工作模式为执行，23 次 Shell（含一条待处理）及两次 TerminalOpen 请求都来自这一解析回退分支。另两次 Browser 请求来自工具内部的站点确认。

权限检查现由公共入口统一收口：先保留拒绝，再应用完全访问；普通模式的具体确认继续交给原审批流程。复查补齐两处边界：工具范围检查早于自动批准；未知或 cmd 解释器仍提取字面拒绝候选，但不因此宣布普通命令已完整获准。三类终端工具共用该规则，没有新增 Shell 模式特例或通用解释器。

自动审查的具体操作说明使用持久审批记录中的快照，作为外部参考资料传入；实际用户授权仍取自原始持久输入。站点或敏感按钮说明不会被当成用户指令，也不扩大完全访问之外的审批权限。

# 正式与临时聊天存储边界

用户已明确要求实现；不增加产品审批步骤。第一阶段 Drizzle 日常读写改造已在 af592a36 完成。

## 行为

正式聊天使用 SQLite。侧边聊天在创建时指定 `storage: "memory"`，普通创建默认 `sqlite`；临时会话的子会话继承内存归属，归属不能通过 metadata 更新改变。两者复用现有 SessionRepository、ConversationRepository、RunRepository、权限、AgentPool、工具及事件投影。审批只在相同存储归属的父子会话间上溯，不把临时 fork 的审批写到正式来源。

临时会话、输入、输入附件引用、消息、片段、普通 Run/Attempt/Task、权限和会话事件保留在 JS 内存。持久化入口根据所属会话选择 SQLite 或内存实现；流式 checkpoint 也遵守归属。SQLite 中不能出现临时聊天记录或会话事件。临时数据随服务进程重启消失，侧边目标关联不保存到 localStorage。

同一应用共享现有项目、附件和工作流存储，不创建第二个 DaemonApplication，避免进程级运行资源互相覆盖或清理。临时 fork 沿用已有历史复制逻辑，正式来源只读；复制后的所有聊天记录归目标内存会话。结构化 conversation 引用继续只读取已提交公开文本。创建、更新和权限关联不能跨会话误写。

2026-10-05 补充：侧边聊天创建时使用 `copyHistory: false`，消息列表从空白开始，主聊天通过发送时的 conversation 引用提供只读上下文；普通 fork 默认复制历史。主动关闭侧边 tab 前提醒并确认，成功停止并删除临时会话及子会话后清掉草稿和缓存；失败保留并允许重试。收起面板和切换聊天不等于主动关闭 tab，不执行销毁。附件、工作流和明确保存的长期记忆不随 tab 销毁。

## 持久资源与记忆

附件字节、附件元数据和工作流仍持久化。来源记录标注正式/临时、来源会话及必要的来源根会话。临时运行的 workflow owner 外键不得引用不存在于 SQLite 的临时 session/input/run；来源信息独立保留，查询和清理不得归到正式主会话或随临时聊天删除误删。

长期记忆库共用。临时聊天默认不执行自动 personalization、session memory checkpoint、自动 remember 和 autoDream；明确调用记住的功能仍可保存。运行普通工具产生的项目文件仍遵循现有工具权限，这与聊天记录的临时生命周期不同。

## 提交与边界

存储实现通过明确的聊天提交/checkpoint/事务接口接入，业务 Repository 继续操作统一内存读模型。SQLite 实现复用 Drizzle 和当前迁移，内存实现使用 JS Map/对象，不使用 SQLite :memory:。

关联写入在同一个协调事务内完成，失败恢复运行内存、临时存储及临时控制记录；成功提交后才发持久事件和唤醒等待者。瞬时流式 delta 保留既有显示行为，不伪装成持久事件。本阶段两个实现都同步提交，入口明确拒绝 Promise，不能把异步提交当作同步成功；后续异步数据库需要等待提交的事务和通知接线，纯缓存查询保持同步。

对外事件共用已有全局序号机制，SQLite 保留共享序号预留上限，但不保存临时聊天事件记录。临时文本增量立即写入 JS 存储，避免无关 SQLite 保存失败后的重载丢掉已接受正文；事务失败仍回滚其内部增量。

本次不实现 MySQL/PG、不增加 SQL 翻译器、不改动无关浏览器标注任务。

## 验证

验证同进程正式/临时创建、fork、发送/工具结果/结束、跨会话隔离；关闭并重开 SQLite 后仅正式记录恢复；临时事件和记录不在 SQLite；失败回滚及提交后通知；持久资源来源及外键；临时自动记忆不写、显式记住仍写。保留既有存储回归和类型检查。

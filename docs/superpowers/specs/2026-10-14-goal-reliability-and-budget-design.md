# Goal 收缩规格：持久目标与空闲续跑

> 修订日期：2026-10-15。状态：收缩实现已完成；验证与真实应用切换边界见 [实施审查](../reviews/2026-10-15-goal-simplification-implementation-review.md)。
> 本文原位替代此前 A/B/C 的增量规格，是后续 Goal 改造的依据；旧实施计划和审查保留为历史记录，不能继续按旧计划扩展准备与验收机制。
> 范围：协议、存储、执行和界面按本规格收缩；不兼容旧 Goal 数据。真实数据库和运行中的应用未在本次交付中切换。
> 审查：[收缩规格审查与修订](../reviews/2026-10-15-goal-simplification-spec-review.md)。
> 实施依据：[Goal 收缩精简实施计划](../plans/2026-10-15-goal-simplification.md)，已按用户授权完成代码改造与集中验证。

## 1. 产品目标与依据

Goal 保存用户希望持续推进的目标。在一次普通执行结束后，只要目标仍然 active、会话空闲且允许执行，服务端就通过现有队列接着推进。Run 指一次有独立身份和终态的执行。

模型在正常执行中理解需求、调查现状、制定计划、修改内容并检查结果。Goal 不要求先把用户指令编译为正式验收表，也不为每轮执行增加独立评审调用。

依据是用户确认的收缩方向，以及本地 Codex 调研：

- 用户提供的 goal-mechanism-full.md 和 goal-analysis-final.md 核实了前端提交、状态同步、暂停及完成展示；仅凭前端分析不能断言后端全部行为。
- [原有调研](../../codex-goal-implementation-research.md)及[同版本原生记录](../../research/codex-goal/2026-10-15-native-followup.json)确认本地 resources/codex.exe 包含 Goal 工具、状态存储及续跑提示，不能把界面启动器当成全部后端。
- [提取的续跑提示](../../research/codex-goal/2026-10-15-continuation.txt)要求模型保持目标范围、核对当前结果、确认真实等待并审查连续阻塞。这些要求不等于存在通用机器验收器。

本文定义本项目的取舍，不声称完整复原 Codex。

## 2. 保留项与删除项

| 保留项 | 保留的边界 |
| --- | --- |
| 显式创建、持久目标、读取当前状态 | 目标独立保存；普通聊天不自动创建目标 |
| 空闲续跑与现有 Run 队列 | 先保存唯一续跑意图；真正开跑前再次检查，不另建调度系统 |
| 暂停、恢复、取消、完成及停止原因 | 用户可控制持续执行；错误和额度停止不能伪装成完成 |
| 请求去重、状态冲突保护、正文版本 | 防止重复执行、旧界面覆盖以及旧 Run 更新新目标 |
| 具体任务等待与权限检查 | 使用现有 Run/批准状态；代理会话存在不代表任务仍在运行 |
| 已有真实用量与可选限制 | 默认不限轮数、不设 Token 预算；用户设置后才限制 |
| 简单目标编辑记录 | 保存用户修改前后正文及时间，便于追溯 |
| 模型自检与三轮阻塞要求 | 模型检查原始目标和当前结果，真正不能继续时报告原因 |

| 删除项 | 后续处理 |
| --- | --- |
| preparing/executing 两阶段、preparation episode、ready 和准备专属工具过滤 | 创建后直接使用正常执行能力及权限 |
| 冻结 requirements、稳定 requirementId、来源逐字引用与替换映射 | 模型按需拆解要求，原始目标始终保留；计划使用现有计划工具 |
| check/artifact_review/tool_result/user_acceptance 分类协议 | 根据任务选择读取、测试和审查方式，不先固化取证类型 |
| 每轮强制 GoalAssessment、预检及终态重复验收 | 替换为简单状态更新；未更新状态的普通回合可以正常结束 |
| Goal 专属 evidenceRefs、摘要依赖、历史证据复核、新鲜度裁决及拒绝代码匹配 | 完成前由模型检查当前状态，不再向 Goal 提交证明包 |
| progressSignals、hostEvidence/hostProgress、工具签名及产物变化评分 | 移除 Goal 对进展的机器证明和评分，不改建另一套 Critic |
| 指定要求的用户验收回执、confirm、refine/pivot 分类和必填变更原因 | 使用普通提问、回答和目标编辑；取消必须可用 |
| “重新整理目标”及验收失败修复入口 | 界面只提供与实际状态相符的继续、编辑、暂停和取消操作 |

以上删除仅针对 Goal 的专属用途。通用工具输出、文件事实、任务身份、用量事件若仍被其他功能使用，应保留；不借此次改造做全项目清理。

## 3. 正常运行流程

1. 用户通过现有目标输入模式提交正文。服务端保存 active Goal 和唯一运行意图，无需准备回合或再次确认。
2. 现有 Run 接纳流程检查会话空闲、待处理用户输入、权限、当前 Goal 状态和用户设置的限制，通过后开跑。
3. Goal 扩展注入完整目标正文与简短状态。执行使用普通工具；复杂任务可使用现有计划工具，简单任务直接做。
4. 一轮正常结束而目标仍 active 时，服务端在没有待处理用户输入、批准或任务等待的条件下安排下一轮。无需 GoalAssessment；缺少状态更新不算执行失败。
5. 模型确认全部目标已完成时提交完成状态；需要用户决定时走现有提问流程；真正受阻时按第 6 节处理。
6. 状态和用量由服务端保存，通过现有通知同步界面。完成后停止续跑，历史目标及会话结果继续可查，不照搬前端完成后清除当前槽位的细节。

待处理的用户输入优先于自动续跑；同一会话不并行派发两个 Goal 根 Run。批准或外部任务尚未结束时不靠新模型回合轮询。旧 Goal 的迟到事件不能重新打开已停止目标。

## 4. 最小状态与模型工具

沿用 active、waiting_user、blocked、paused、completed、cancelled 六种状态，不再叠加阶段字段。

| 数据 | 用途 |
| --- | --- |
| id、sessionId、objective、objectiveVersion | 识别目标、保存完整原文、隔离正文修改前后的运行 |
| status、revision、currentRunId、时间戳 | 状态控制、界面冲突保护、绑定当前运行 |
| reason/stopReason、可选 wait | 解释停止或等待；wait 只保存具体问题、批准请求或任务身份 |
| maxAutoTurns、autoTurnsUsed、tokenBudget、usage | 复用现有次数和用量能力，不再追加预算平台 |
| 简单正文版本记录 | 保存正文前后版本、用户请求身份和时间；取消必填变更类型、原因及条件快照 |

保留 requestId 去重以及 Goal 与 Run 的可信绑定。正文真正改变才递增 objectiveVersion；状态和用量变化不增加正文版本，用量更新也不制造界面编辑冲突。

模型只需要两个 Goal 工具：

- GoalRead：读取宿主绑定的当前目标、状态、等待、停止原因和用量；不提供证据索引或冻结条件。
- GoalUpdate：按需提交状态变化、向用户提问或登记具体任务等待。三类输入互斥，不包含要求清单、证据引用或进展评分。

| GoalUpdate 请求 | 模型提供 | 宿主处理 |
| --- | --- | --- |
| 状态变化 | completed、blocked，或响应用户明确暂停请求的 paused，以及简短说明 | 核对绑定与当前状态，保存状态变化 |
| 提问 | 问题正文 question | 生成问题身份，绑定当前目标和正文版本，置 waiting_user；复用已有回答界面 |
| 任务等待 | targetRunId 和沿用的等待期限 deadlineAt | 验证具体任务归属，保持 active 并保存 wait，交现有观察器处理 |

goalId、objectiveVersion、发起方 runId 和问题身份均由宿主绑定；模型只能提供需要观察的具体 targetRunId，不能选择其他会话来修改目标。提问和任务等待只是可选控制动作，普通回合不必报告。

继续执行不需要调用 GoalUpdate。创建、恢复、取消、正文编辑和预算修改由明确的用户操作进入现有应用接口；普通聊天不让模型随意改写这些设置。GoalUpdate 不能自行恢复目标、修改正文或提高预算。

GoalUpdate 在同一事务中核对当前绑定、状态、停止条件和请求结构。完成、阻塞、提问及任务等待只接受当前 active 且允许执行的绑定；不能覆盖用户暂停、取消、完成或宿主限制停止。当前 Run 身份即使未变，迟到提交也不能绕过这些检查。宿主不进行要求覆盖、证据引用或文件内容裁决。旧目标工具协议直接移除，不提供旧名别名或双格式解析。

## 5. 澄清、编辑与完成

**澄清。** 对范围已明确的目标直接工作。诸如“优化系统”的目标可以先在已有授权和权限内调查；真正缺少关键选择时通过 GoalUpdate 提问并复用现有回答界面。UI、调研、文档任务不强迫用户填写量化指标。

提问后宿主记录与当前目标、正文版本和问题绑定的等待，状态为 waiting_user，不再自动续跑。有效答复只清除对应等待，确认没有其他停止条件后才恢复 active 并检查续跑资格；过期问题的回答不能恢复新目标。普通聊天不解除用户暂停、预算停止或其他未解决等待。批准请求继续沿原批准链路处理，不增加第二套 Goal 审批。

**编辑。** 用户编辑完整正文即可，不必选择 refine/pivot、要求 ID 或填写变更原因。打开编辑器与取消编辑都不改变目标。成功保存后使旧运行绑定、问题等待、批准关联、外部等待观察及旧续跑意图失效，通过现有控制请求停止旧运行及其关联任务。旧批准不能授权新版本操作，迟到回答或任务事件不能改变新版本状态；迟到真实用量仍可记账。已执行操作不承诺回滚。

编辑不自动恢复 paused 或 blocked，也不解除预算等宿主限制；这些情况仍须显式继续并通过原有检查。原先 active 的目标，以及仅等待旧版本问题或批准的目标，清除旧关联后在没有其他停止条件时由宿主恢复 active，再按会话空闲及接纳规则执行新正文，不得并行启动新旧目标。completed/cancelled 目标通过显式新建开始后续工作。修改目标不清零累计用量和次数。

**完成。** 模型在当前工作状态下重新对照原始目标及用户引用的要求，使用适合任务范围的检查。子任务改写了文件，就读取当前文件或重新执行受影响检查；任务仍运行且结果可能变化时，不能提前宣告全部完成。最终回复说明结果、必要的验证及尚存限制。

本次明确取消“Goal 宿主必须拒绝旧读取证据、再接受新证据”的通用验收承诺。用户可以要求模型进行当前状态检查和针对性测试；Goal 不再判断工具结果是否在语义上证明任意目标。模型可能误判完成，这一能力边界必须如实保留。

## 6. 等待、阻塞与恢复

**具体任务等待。** 模型通过 GoalUpdate 提交当次 targetRunId 和等待期限；宿主核对可信父子归属后，绑定当前正文版本及发起方 Run，保存等待并交现有观察器处理。正常 pending/running 保持 active + wait，不派发模型；completed 清除等待，重新检查状态、版本及续跑资格，只接纳一次后续检查。failed/interrupted/cancelled、等待记录不存在、归属不符或期限耗尽，由宿主置 paused 并保存具体原因，不自动重启任务。临时读取失败或一次观察超时不等于任务终止；继续核对同一任务，不能因代理会话尚在就判为 running。

**连续阻塞。** 续跑提示要求模型区分实际推进、已确认仍在工作的等待、没有进展；同一真正阻塞连续至少三个 Goal 回合且已无可行行动时，调用 GoalUpdate 标为 blocked。一个回合内多次工具失败或轮询不能冒充三个回合。需要用户选择时及时提问，不为凑三轮反复询问。

阻塞是否相同、是否仍有可行行动由模型根据会话和当前事实判断。宿主保存状态变更与运行身份，不比较自由文本相似度、不计算 Progress Score、不强制每轮进展报告，也不承诺独立检测所有语义空转。用户恢复 blocked 后重新审查本次阻塞，不继承先前的“三轮已到”结论。

**失败与恢复。** Run 真实失败、用户停止和限制耗尽均停止新增自动工作，保存可理解的原因。用户停止先持久化暂停并撤销续跑意图，再通过原控制请求中断；中断不能因暂停请求失败而被卡住。暂停未成功时界面必须报告并允许重试。显式恢复仍检查权限、等待和预算，不绕过既有限制。进程重启沿用保守恢复：不自动重放未确认工作，无法确认的执行暂停并由用户继续。

## 7. 用量与默认限制

- 自动续跑次数默认不限，沿用现有 0 表示不限；Token 预算默认缺省。取消历史文档里的默认 20 次、准备调用次数等专属限制。通用单轮运行限制和用户中断继续有效。
- 复用已有每次真实模型尝试的用量记录和可信 Goal/后代归属。失败、中断及迟到事件仍记账，去重后不叠加父子汇总；编辑、暂停和恢复不清零。
- 保留已有规范化口径：完整输入 Token（包含缓存）加输出 Token，适配器负责避免重复计算。Goal 不自行猜提供商字段，不改造成价格系统。
- 有显式预算时，达到已知限制或用量不完整且无法确认余额，就暂停并说明原因；未设预算时只展示用量不完整，不因此强制停工。
- 排队、真正派发及现有执行边界继续检查用户设置的限制，停止新增工作。已在执行中的请求和迟报用量可能超额，不承诺绝对硬顶；不为收尾额外派发模型请求。

用量作为事实保存，完成语义交由模型判断；删掉证据协议不影响身份、权限和预算检查。

## 8. 职责边界

| 位置 | 实际负责的事情 | 边界 |
| --- | --- | --- |
| Desktop / Client | 输入、查看、编辑、暂停、继续和取消；提交用户操作 | 不本地调度、不从文字猜状态、不展示正式验收表 |
| protocol | 字段、状态、长度等结构校验 | 不判断目标含义和证据有效性 |
| SessionGoalService | 保存目标状态，接纳用户操作，绑定 Goal/Run，决定续跑资格 | 不整理正式条件、不检查文件、不做模型工作规划 |
| GoalRepository / 现有事务 | 目标、简单正文记录及已有用量的存取、去重与一致性 | 不调模型、不执行工具、不新增通用审计服务 |
| RunAdmission / RunControl / 队列 | 用户输入优先、单次接纳、开跑复查、中断及撤销 | 不判断用户目标是否完成 |
| 等待观察器 / Run 状态查询 | 核对具体任务归属和真实终态，退避观察、唯一恢复 | 不根据会话存在猜任务状态，不因超时重启任务 |
| Runtime / Goal 扩展 | 注入目标与简短续跑提示，提供绑定工具，传递状态及用量事件 | 普通 Run 不依赖 Goal；不增加隐藏准备权限 |
| 模型与现有计划工具 | 理解范围、选择步骤、执行检查、完成自检和阻塞判断 | 不修改用户目标、权限或预算，不以计划更新充当实际进展 |

不新增 Critic、准备代理、需求管理服务、证据平台、进展评分器、定时唤醒系统或第二套执行队列。

## 9. 界面与数据切换范围

目标栏默认只显示简短状态、目标摘要及适用操作；展开看完整正文。次数和用量放已有二级运行详情，默认不展示、不要求填写预算。需要用户回答时展示现有提问交互；编辑要有明确保存和取消，不把输入框长期锁在变更模式。继续遵循 apps/desktop/DESIGN.md 和已有组件，不新建验收页面。

后续实现只支持收缩后的 Goal 数据结构，移除旧准备、评估、证据和验收请求格式，不迁移、转换、回填、双读或自动接管旧目标。数据切换应先停止旧 Goal 及其待派发工作，旧目标不进入新续跑路径；处理范围仅限 Goal 自有数据和派发意图，保留会话、消息、Run 与工具历史。现有通用事件、用量接口和非 Goal 数据不因此失效。

本轮不执行数据清理、重建或恢复真实会话；这些操作也不能夹带在文档修改中。后续实施计划须明确具体存储处理范围后再执行。

## 10. 收缩后的验收重点

后续实现集中验证以下行为，不按已删除的证据协议保留测试负担：

1. 创建明确目标后直接进入正常执行，无准备回合、ready 或正式条件冻结；普通回合未调用 GoalUpdate 仍可续跑。
2. 用户输入优先、同会话不并行派发 Goal 根 Run，重复事件不重复续跑；批准和外部任务等待期间不空耗模型。
3. 暂停/取消能阻止自动续跑及迟到完成覆盖；取消编辑不改变目标；保存编辑后旧 Run 不能完成新版本，编辑不隐式恢复暂停或限制停止。
4. 提问有明确入口；回答只解除对应等待，不能解除用户暂停或预算停止；正文编辑使旧等待及批准关联失效，过期回答不影响当前目标。
5. 任务等待有明确入口，读取当次 Run 真实状态，结束只恢复一次；临时观察失败不导致重启任务，任务失败或等待失效明确暂停并说明原因。
6. 默认不限次数和 Token；用户限制生效、用量不重复、迟到用量不丢；无预算时不因用量不完整停工。
7. 完成/阻塞工具仅接受当前绑定及允许状态；被拒时说明身份或状态错误，不返回旧证据校验提示。宿主不以结构测试通过宣称已经证明语义完成或三轮阻塞判断可靠。

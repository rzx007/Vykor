# Write 失败后的内容复用 Spec

> 状态：已完成 spec 审核修订、实施计划、实现、范围验证与最终子代理代码复审。用户要求的连续推进流程已执行。

## 1. 问题与目标

只读检查最近五个开发会话，Write 调用 30 次，其中 18 次失败。2026-10-01 的 x2 会话生成约 24 KB HTML 的两轮请求分别耗时 590 秒与 419 秒，工具约 2 秒返回失败；2026-10-02 的 x3 会话生成约 24 KB HTML 用了 580 秒，Write 约 1.9 秒成功。后者覆盖小文件时还经历了缺少 `overwrite`、把布尔值写成字符串、最终成功的三轮往返。

本轮只解决一个问题：模型已经提供完整文件内容后，后续调用可以引用这份内容，修正目标路径或显式覆盖参数，通过原有执行流程应用修改，不必再次生成整份文件。

不承诺缩短首次生成时间，也不自动重试或推断用户的覆盖意图。

## 2. 范围与简化选择

采用现有会话内存历史作为内容来源，不新增磁盘草稿、数据库表、全局缓存、后台任务、依赖或配置。

比较过的方案：

- **本轮方案：引用既有调用参数。** 内容已经保存在 assistant 工具调用历史里；在执行准备阶段展开引用，再走校验、失败去重和权限。
- **磁盘草稿或独立恢复服务。** 可以跨历史压缩长期保留内容，但会引入保存、清理、访问控制等额外职责，本轮不做。
- **专用 Apply 模型。** 需要额外模型请求与服务配置，不能直接解决已生成内容被重复输出的问题，本轮不做。

本轮不改变 Edit 匹配、参数包装归一化、网络重试、工具调用流式显示、权限模式或模型选择；不增加预检查工具。已有 Read/Glob 可用于了解目标，首次写入与覆盖的文件状态仍以实际执行时为准。其他会话正在修改参数归一化相关文件，实施必须保留其改动。

## 3. 模型可见接口

Write 保留 `file_path`、`content`、`overwrite`、`expected_sha256`，新增字符串 `content_from`，值为之前 Write 调用的工具调用 ID。

```json
{
  "file_path": "C:/workspace/index.html",
  "content_from": "call_previous_write",
  "overwrite": true
}
```

- `file_path` 始终必填。
- `content` 与 `content_from` 必须且只能提供一个；空字符串是合法的完整文件内容。
- 引用只复用 `content`，不继承原路径、`overwrite`、`expected_sha256` 或任何权限。
- 新调用的目标路径和覆盖意图必须显式给出，仍受原有系统目录、沙箱、覆盖和 hash 检查约束。
- 不将字符串 `"true"` 转为布尔值，不修复非法 JSON，不猜测缺失内容。
- Write 的说明解释引用的用途；有可复用内容的失败反馈给出源调用 ID 和短示例，不复制文件正文。

为让模型能发出短引用，Write schema 的必填字段调整为 `file_path`，两种内容形式的互斥和内容必填在执行准备阶段明确验证。保持简单 schema，不增加根级 `oneOf`，以兼容当前参数包装归一化。即使顶层带有 `file_path` 而被归一化提前认为合法，展开阶段仍会拒绝缺少内容或非法引用，不丢弃旁带字段来猜测用户意图。

直接调用 `fileWriteTool.execute` 只接受已展开的字符串 `content`。发现自身字段 `content_from` 仍存在时一律返回 `invalid_input/not_started`，同时提供正文和引用也不能绕过；校验位于路径解析和任何文件访问之前。空字符串仍合法。

## 4. 代码边界与运行流程

### 4.1 工具声明

`ToolDefinition` 增加一个可选的声明式字段：

```ts
inputReuse?: { property: string; referenceProperty: string };
```

Write 声明 `{ property: "content", referenceProperty: "content_from" }`。这不是模型可执行的回调，也不传到提供商 API；没有该声明的其他工具完全沿用现有流程。引擎不了解 Write 的文件系统实现，只负责按声明展开一个参数引用。

### 4.2 引擎执行准备

`prepareToolCalls` 增加当前消息历史参数，QueryEngine 传入其已持有的 `messages`。一个小的 core 内部函数负责引用解析，不导入 tools/services，不查询数据库、不读取文件。

流程为：JSON 解析标记检查 → 查实际注册工具 → 既有参数归一化 → 内容引用展开与互斥检查 → 参数校验 → 失败调用记忆检查 → 权限检查与预览 → hooks → 工具执行。

内容引用展开后，权限、预览、失败去重和工具执行使用同一份有效参数。`content_from` 从有效参数移除，填入真实 `content`；不修改来源对象，也不改写已落盘的原始模型调用事件。

### 4.3 来源条件与有效期

- 只在当前引擎实际持有的消息历史里查找。
- 来源 ID 在全部历史工具调用中必须唯一，包含跨工具重名的检查。来源必须为同名工具的既往调用，且没有 `inputError`。
- 对应 `tool_result` 必须出现在来源调用之后、当前批次之前；不能把错序或属于其他同 ID 调用的结果当作来源已完成。
- 来源参数必须直接包含字符串 `content`；不得用 Shell 或其他工具的参数作为来源。
- 排除当前调用和同批次所有调用 ID；不支持前向引用、自引用或同批次依赖。
- 找不到来源、调用 ID 有歧义、内容被历史压缩移除、来源只剩未展开引用时，返回 `invalid_input/not_started`，不进入权限或执行。
- 不递归追踪引用链。内存历史中已展开的合法调用可以成为来源；重启、恢复或压缩后仍需满足上面的来源条件，不承诺跨这些边界保留引用。
- 来源成功或失败均可复用内容，但只复用数据。新的动作仍由模型显式请求，通过当前工具权限和执行时文件检查；不自动重新执行未知结果或被拒绝的动作。

展开后的内存调用仍含完整正文，后续模型请求也会携带这份历史内容。该方案减少重新输出正文，不承诺降低输入上下文体积；不为此增加缓存。

### 4.4 失败反馈

来源检查与提示共用同一判断：只对声明了内容复用、没有 `inputError`、有完整字符串内容且能够成为下一轮合法来源的失败调用，在既有错误正文后添加短提示。提示列出当前工具调用 ID、`content_from` 用法，并要求明确修正路径/覆盖参数或先核对实际状态。结果未知时仍明确要求先核对状态；权限/策略拒绝不因此获得重试授权。不暴露内容正文，不在日志添加内容，不改变原始 `failureKind`、`executionState` 和既有恢复提示。

失败记忆保存和查询均使用展开后的有效参数。同参重试不能只靠换引用 ID 绕过失败保护；修改显式参数或已有新证据时按原规则处理。Write 不设置 `safeToRetry=true`。

## 6. 验收

1. 首次 Write 提供完整长文本；第二次只提供源调用 ID 与 `overwrite: true`，写入字节与首次内容完全相同，第二次模型参数不含正文。
2. 首次默认覆盖失败，反馈给出引用 ID；第二次显式覆盖成功，执行时仍检查当前文件与 `expected_sha256`。
3. 权限检查、权限请求和 pre-tool hook 均拿到展开的真实内容；拒绝时执行次数为零。
4. 内容与引用同时提供、两者均未提供、引用不存在、来源工具不符、来源非法 JSON、来源无结果、跨工具重复 ID、错序结果、自引用与同批次引用都在执行前失败；不可作为来源的失败调用不给复用提示。
5. 空内容合法；来源对象不被修改；其他工具的处理不变。
6. 已失败同参调用通过引用重发仍命中原有失败保护；新证据和实际参数改变的规则不变。
7. 压缩后来源丢失时清楚报错，不访问数据库或凭空生成内容。
8. 直接执行 Write 缺少字符串内容或仍含引用时在访问文件之前拒绝；既有创建、原子覆盖、目录/符号链接、沙箱和 hash 测试继续通过。
9. 范围测试、core/tools 类型检查、文档检查与相关架构检查通过；不使用真实模型、真实用户任务文件或真实写入操作来跑回归。

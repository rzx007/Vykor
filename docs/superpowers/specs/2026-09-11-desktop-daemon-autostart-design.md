# Desktop daemon 常驻设置与首次引导设计

## 目标

在 Desktop 中提供 daemon 常驻的可视化设置，并只对真正首次安装的新用户展示一次低打扰引导。用户开启后，daemon 会在当前用户登录系统时启动，并在异常退出后由操作系统恢复，从而保证关闭 Desktop 后，定时任务和后台工作仍可继续。

本功能复用现有 `daemon.autoStart` 和跨平台系统服务能力，不创建第二套自启机制或额外后台进程。

## 用户体验

### 设置入口

在「设置 → 常规 → 常规」中新增一行：

- 名称：`后台持续运行`
- 说明：`登录系统后自动启动 daemon，并在异常退出后恢复，让定时任务和后台工作持续执行。`
- 控件：开关

开启开关等同现有 `vk daemon install`：写入 `daemon.autoStart = true`，安装当前用户范围的系统启动项，并立即启动 daemon。

关闭开关等同现有 `vk daemon uninstall`：写入 `daemon.autoStart = false`，停止 daemon 并删除系统启动项，但不删除会话、定时任务或其他用户数据。之后 Desktop 需要本地 daemon 时，仍可沿用当前的按需启动行为。

操作期间开关不可重复点击。操作失败时恢复原来的界面状态，并在设置项附近显示具体、可重试的错误。设置页加载和应用重新获得焦点时刷新真实状态，以反映 CLI 或其他客户端做出的修改。

### 首次安装引导

引导复用侧边栏底部当前静态的「开始使用 1/3」位置，不新增弹窗、悬浮层或系统通知。符合条件时，原占位替换为一张紧凑卡片：

- 标题：`保持后台运行`
- 说明：`关闭 Vykor 后，定时任务和后台工作仍可继续。`
- 主操作：`开启`
- 次操作：`暂不开启`

引导不会自动消失，也不会抢占键盘焦点。

点击「开启」后，按钮显示处理中状态。系统服务安装并启动成功后，引导永久消失；失败时卡片保留，在原位显示简短错误和「重试」。

点击「暂不开启」后，引导立即永久消失。原来的「开始使用 1/3」占位不恢复，整个卡片区域消失。用户以后仍可在设置页手动开启。

## 展示条件

只有同时满足以下条件时才展示首次引导：

1. 当前用户被识别为真正首次安装的新用户；
2. 首次引导状态为 `pending`；
3. `daemon.autoStart` 当前为关闭；
4. Desktop 启动和 daemon 状态读取已经完成。

如果引导显示前已经通过 CLI 或其他方式开启常驻，则不展示，并把引导记为已完成。判断完成前不渲染引导，避免启动时闪现。

## 新用户识别与持久化

新版本第一次运行时，由 Electron 主进程在写入本功能自己的标记之前检查既有 Desktop 用户数据：

- 已存在历史 Desktop 数据：识别为升级用户，写入老用户标记，不展示引导；
- 不存在历史 Desktop 数据：识别为首次安装用户，初始化引导状态为 `pending`。

保留用户数据后卸载再重装仍视为老用户，不重新展示。

Desktop 偏好增加独立的安装身份和引导状态。引导状态使用明确枚举：

- `pending`：符合其他条件时可以展示；
- `enabled`：用户通过引导开启，或展示前已发现常驻开启；
- `dismissed`：用户选择暂不开启。

引导状态不与 `daemon.autoStart` 混用。用户以后关闭常驻服务，不会让引导重新出现。

## 组件边界与数据流

Electron 主进程新增 Desktop daemon 常驻适配层。它组合 `@vykor/server/daemon-host` 的统一 controller 与 Desktop 自己的首次引导状态。server controller 负责配置值、系统服务安装状态、协调与失败恢复；Desktop 适配层负责：

- 调用 controller 查询、开启和关闭常驻；
- 初始化安装身份；
- 完成或忽略首次引导。

CLI 与 Desktop 共用 server controller。Preload 只向渲染层暴露固定能力：查询状态、开启、关闭和处理首次引导。接口不接受任意命令、可执行文件或路径。

设置页和侧边栏共用该接口。渲染层只管理加载、提交和错误展示，不自行推断系统服务是否已安装。

运行流程如下：

```text
Desktop 启动
  → 主进程初始化安装身份和引导状态
  → 查询 daemon.autoStart 与系统服务实际状态
  → 渲染层获得统一快照
  → 设置页显示真实开关状态
  → 侧边栏按展示条件决定是否渲染首次引导

用户开启
  → 主进程写入 daemon.autoStart = true
  → 安装或启用当前平台的用户级系统服务
  → 启动并确认 daemon 状态
  → 返回新快照
  → 开关保持开启，引导记为 enabled 并消失

用户关闭
  → 主进程写入 daemon.autoStart = false
  → 停止 daemon 并删除系统启动项
  → 返回新快照
  → 开关显示关闭，引导状态保持不变
```

## 状态真实性与失败处理

设置开关不能只展示配置文件中的布尔值。统一快照应区分配置意图与系统服务的实际结果，避免出现配置为开启但服务未安装的假成功。

开启或关闭只有在现有系统服务操作成功并重新读取状态后才算完成。部分步骤失败时，接口返回可理解的错误，渲染层恢复到重新读取的真实状态。首次引导开启失败时不写入 `enabled`，用户可以重试或选择「暂不开启」。

Windows、macOS 和 Linux 均复用现有实现：Windows 当前用户计划任务、macOS LaunchAgent、Linux systemd user service。远程 daemon 不在本功能范围内。

## 安全边界

- 系统服务操作只通过 CLI/Desktop 主进程调用的 `server/daemon-host` 本地入口发生，不暴露为 HTTP API。
- 渲染层不能拼接或执行 CLI 命令。
- 所有操作限定在当前用户范围，不请求管理员或 root 权限。
- 关闭常驻不删除任何业务数据。
- 本功能不改变 daemon、SessionStore、Scheduled Tasks 或 Agent 的运行模型。

## 测试与验收

自动化测试至少覆盖：

- 全新安装、引导为 `pending`、常驻关闭时展示；
- 老用户升级不展示；
- 保留数据后重装不展示；
- 常驻已经开启时不展示，并完成引导状态；
- 点击「暂不开启」后永久不再展示；
- 引导开启成功后消失；
- 引导开启失败时保留、显示错误并允许重试；
- 设置开关正确调用开启和关闭能力；
- 失败后开关回到真实状态；
- 通过 CLI 修改后，Desktop 刷新得到新状态；
- Windows、macOS、Linux 的服务状态正确映射；
- 既有侧边栏、设置页以及 Desktop 按需启动 daemon 的行为不回归。

人工验收需要在支持的平台安装包中确认：首次安装只出现一次引导；升级安装不出现；开启后关闭 Desktop，daemon 和定时任务仍能按现有机制运行；关闭后系统启动项被移除且用户数据保留。

## 不在本次范围内

- 恢复或实现「开始使用 1/3」原占位的其他引导内容；
- 为老用户补发引导；
- 用户忽略后再次提醒；
- 系统级或无人登录时运行 daemon；
- 远程 daemon 部署与管理；
- 修改 daemon 的任务恢复语义。

# 对话附件功能完整复盘

> 当前说明：本文记录 2026-08-29 当时轨迹；Docker 会话资源目录方案后来已删除，现行附件边界见 [附件能力退出 Agent Runtime](./2026-09-02-attachment-tool-overrides-design.md)。

> 日期：2026-08-29  
> 范围：从附件领域模型、上传与持久化，到图片原生输入、OCR 降级、安全文本读取、生命周期治理和设置页发布收口  
> 当前分支：`codex/attachment-release-closeout`

## 1. 一句话结论

这轮工作已经把“对话附件”从一个上传按钮，做成了一条可持久化、可恢复、可追踪、可降级、可清理的完整运行链路。

当前真正完成并适合发布的范围是：

- 常见图片附件：模型和供应商都支持图片时，直接交给模型；否则由主 Agent 按需调用本地 `ImageToText` 做 OCR。
- 安全文本和代码附件：小文件直接放进提示词，大文件通过只读资源按行读取。
- 会话生命周期：附件跟随发送、排队、重试、编辑、分叉、重启、压缩和历史消息稳定存在。
- 本地存储治理：支持去重、租约保护、延迟删除、安全回收、完整性扫描、备份恢复和设置页可视化。
- 不支持的文件不会被悄悄忽略，而是在调用模型前明确阻止并说明原因。

这并不等于“通用文件平台已经完成”。PDF、Word、Excel、PowerPoint、压缩包、未知二进制、文件夹上传和断点续传仍然不在当前发布范围内。这是有意收窄的产品边界，不是遗漏。

## 2. 最初的问题，为什么不能只做一个上传按钮

最开始的需求看起来很直接：对话框支持上传附件。但真正把附件交给 Agent 使用，需要同时回答下面的问题：

1. 文件由谁保存，保存多久，重启后还能不能找到？
2. 一条输入引用了哪些附件，顺序如何保持？
3. 上传成功但发送失败时，附件和输入怎么恢复？
4. 模型支持图片、供应商接口却不支持图片时，应该走哪条路？
5. 自定义模型的图片能力无法自动判断时，如何安全配置？
6. 模型不支持图片时，OCR 是自动执行，还是作为 Agent 工具按需调用？
7. 文本附件多大可以直接放进上下文，多大必须按需读取？
8. PDF、Office、压缩包和未知二进制该如何处理，能不能误当文本？
9. 去重后的文件怎样统计空间，什么时候可以安全删除？
10. 数据库、文件系统、备份和恢复之间如何避免出现“记录还在但文件没了”的状态？

因此，这次没有采用 MVP 式的“先把文件路径塞进消息”。我们先建立附件的长期语义，再逐层接入上传、消息、模型路由和存储治理。

## 4. 最终运行流程

附件从本地文件进入 Agent，大致经过下面这条链路：

```text
用户选择 / 拖拽 / 粘贴
        │
        ▼
Electron Main 读取真实文件路径并以流的方式上传
        │
        ▼
Daemon 校验大小、文件名和 MIME，写入内容寻址 Blob
        │
        ├── 相同内容已经存在：复用物理 Blob
        └── 新内容：暂存完成后原子移动到正式位置
        │
        ▼
Renderer 只拿安全元数据，组成当前输入框的附件草稿
        │
        ▼
发送时一次性写入：用户输入 + 有序附件引用 + 运行请求
        │
        ▼
附件能力路由
        │
        ├── 安全文本
        │     ├── 小文件：作为“不可信用户数据”内联
        │     └── 大文件：生成只读 attachment:// 资源，由 Agent 按行读取
        │
        ├── 图片
        │     ├── 模型支持 ∩ 供应商支持：原生图片输入
        │     └── 否则：暴露附件提示，主 Agent 按需调用 ImageToText 本地 OCR
        │
        └── PDF / Office / 压缩包 / 二进制：调用供应商前明确阻止
        │
        ▼
运行、工具记录和结果进入持久化历史
        │
        ▼
会话压缩、重试、分叉、重启、备份和恢复继续保留附件语义
```

这里有两个重要原则：

- Renderer 不长期持有真实本地路径。路径只在 Electron Main 中用于读取文件，真正可持久化的身份是 `attachment asset id`。
- 附件内容始终被标记为用户提供的不可信数据，不能因为文件里写了类似系统指令的文字，就获得更高权限。

## 5. 核心数据模型

### 5.1 附件资产和输入引用分开

系统没有把“文件”和“消息里的附件”混成一张表。

- `attachment_asset` 表示不可变的附件资产，包括内容哈希、大小、媒体类型、状态和物理 Blob 信息。
- `session_input_attachment` 表示某次会话输入以什么顺序引用了哪些资产。

这样做解决了三个问题：

1. 同一个附件可以被多个输入引用，而不需要复制文件。
2. 删除一条消息不会误删仍被其他输入使用的 Blob。
3. 重试、分叉和恢复时可以复制引用语义，不需要重新上传。

### 5.2 派生表示单独缓存

OCR 结果不是覆盖原始图片，而是作为附件的一种派生表示保存。缓存键包含处理器和版本信息，因此 OCR 引擎或规则更新后，可以生成新版本而不会混用旧结果。

只有实际完成的表示会进入会话压缩目录。系统不会为了让摘要看起来完整，虚构一个尚未执行的 OCR 或文本摘要。

### 5.3 租约保护正在使用的文件

运行或只读资源正在使用附件时，会创建 `attachment_lease`。垃圾回收前必须确认：

- 没有会话输入仍在引用；
- 没有有效租约；
- 共享同一内容哈希的其他资产不需要这个 Blob；
- 已经过逻辑删除的宽限期。

这使“清理空间”和“运行中的 Agent 继续读取附件”不会互相踩踏。

### 5.4 四次数据库迁移

| 迁移 | 作用 |
| --- | --- |
| `0013_attachments.sql` | 建立附件资产和基础存储模型 |
| `0014_session_input_attachments.sql` | 建立有序输入引用，并补齐消息附件与转换信息 |
| `0015_attachment_representations.sql` | 保存 OCR 等派生表示和处理状态 |
| `0016_attachment_lifecycle.sql` | 增加运行租约，支撑安全清理和生命周期管理 |

## 6. 分阶段回顾

### 阶段 1：先让附件成为可靠资产

这一阶段没有做花哨的界面，主要解决“文件能不能可靠地进系统”。

完成内容：

- 定义附件协议、状态和限制。
- 建立内容寻址 Blob 存储：物理文件按内容哈希管理，相同内容天然去重。
- 使用流式上传，避免一次性把大文件读入内存。
- 校验文件名、路径、大小和实际内容类型。
- 建立上传、查询、读取、删除等 HTTP 和 Client 能力。
- 增加启动恢复：处理中断留下的暂存文件或未完成状态能够被识别和收口。

阶段复审后又补强了 Blob 边界、MIME 判断、能力检查和恢复测试。这说明底层存储一旦出错，后续所有 UI 和模型能力都会建立在不可靠基础上，因此最早期的测试投入非常值得。

### 阶段 2：让附件真正属于一条输入

这一阶段解决的不是“文件存在”，而是“哪次输入使用了哪些文件”。

完成内容：

- 输入文本、有序附件引用和运行请求作为一次提交写入。
- 幂等指纹包含附件引用，重复请求不会形成语义不同但指纹相同的输入。
- Snapshot、SSE 和 Client 都能传递附件信息。
- 排队、重试、分叉、重启和历史消息投影保持相同引用。
- 删除附件前检查持久引用，防止误删。
- 明确不兼容旧的实验性附件数据格式；检测到旧格式时直接给出清晰错误。

最关键的经验是：附件必须在“输入被接纳”的那一刻持久化，不能等消息渲染完再补记录。后者在崩溃、重试和并发时很容易丢失关系。

### 阶段 3：桌面端上传和消息体验

这一阶段把底层资产能力接入真实对话流程。

完成内容：

- 文件选择、拖拽和剪贴板图片。
- Electron Main 读取真实路径，Renderer 只接触安全元数据。
- 每个对话输入框拥有独立附件草稿。
- 通过 `draftId + taskId` 防止切换会话或异步完成时把附件写进错误的输入框。
- 上传进度、取消、失败重试、移除和附件-only 发送。
- 新建会话的第一条输入也能携带附件。
- 乐观消息与 SSE 服务端结果能够对账，避免同一个附件卡片出现两份。
- 历史附件支持预览、打开和另存。
- 编辑历史消息时附件保持只读。
- “添加文件夹”图标继续保留，但明确禁用并提示后续开放。

这里最难的并不是卡片样式，而是上传任务、当前草稿、会话切换和服务端事件四者之间的竞态。最终选择“发送时冻结一份不可变快照，再和服务端结果对账”，比让 UI 一直引用可变草稿更稳定。

### 阶段 4：图片原生输入和能力判断

这一阶段先建立正确的图片路由，没有急着把 OCR 混进来。

完成内容：

- 模型图片能力使用 `native / unsupported / unknown` 三态，而不是简单布尔值。
- 自定义模型在设置页明确选择“图片能力未知 / 支持图片 / 不支持图片”。
- 同时检查模型声明和供应商适配器能力。
- 只有两者都支持当前图片类型，才构造供应商的原生图片输入。
- 图片从 Blob 安全物化，并保持附件顺序。
- OpenAI、Codex、Anthropic 等适配器分别完成输入转换。
- 不满足条件时在请求供应商之前阻止，并保存路由决定，方便排查。

为什么要三态：自定义模型名称本身不能可靠证明它支持图片。把“未知”当“支持”会在运行到供应商后才失败；把它当“明确不支持”又会掩盖配置问题。因此未知必须成为一种可见、可配置的状态。

### 阶段 5：用本地 OCR 做安全降级

用户明确要求移除 `ImageToText` 原有的远程视觉模型能力。最终它只承担一个职责：当主 Agent 不能直接看图时，读取图片中的可见文字。

完成内容：

- 接入 light-ocr 本地处理链路。
- 统一图片输入规范化和 OCR 输出格式。
- OCR 表示按处理器版本缓存，避免重复识别。
- `ImageToText` 只接受 `attachment_id`、`image_path`、`image_url` 三者之一，不再接收视觉提示词。
- 移除工具内的远程视觉模型调用。
- 当图片不能原生输入时，向主 Agent 暴露一个不可信附件资源提示，由 Agent 按实际任务决定是否调用 `ImageToText`。
- 工具或 OCR 主机不可用时，在请求供应商前明确阻止。
- OCR 没识别到文字时返回明确的 `no_text_detected`，不编造描述。
- 工具调用、附件身份、OCR 结果和最终回复能够在记录中对应。

这里必须强调：OCR 不是视觉理解。它可以读截图中的按钮文字、文档照片中的段落，但不能可靠回答“照片里是什么场景”“柱状图哪根最高”“这个物体在另一个物体左边还是右边”。无视觉能力的模型遇到这类问题，仍然应该明确说明能力不足。

这一步还暴露了真正的桌面打包问题：原生依赖、Electron `asar` 解包、运行时资源和 `createRequire` 命名冲突都必须在完整仓库测试中处理。只在源码测试里通过，不代表安装包里的 OCR 能工作。

### 阶段 6：安全文本和代码附件

这一阶段主动收窄了范围：先把文本和代码做对，暂不支持 PDF 和 Office。

完成内容：

- 通过可信 MIME、文件签名和安全扩展名共同判断文本候选。
- 只接受严格 UTF-8、带 BOM 的 UTF-8，以及带 BOM 的 UTF-16LE / UTF-16BE。
- 拒绝无效字节、NUL 字节和异常控制字符，不猜测 GBK 等本地编码。
- 小于等于 16,000 字符的文本作为不可信用户数据内联。
- 大文本只提供不超过 3,000 字符的预览，并生成 `attachment://asset-id/name` 只读资源。
- Agent 复用现有 `Read` 工具按行读取，默认最多 2,000 行，避免一次吞入超大文件。
- PDF、Office、压缩包和未知二进制统一在模型调用前阻止。
- Docker 场景使用独立只读会话资源目录，不直接挂载 Blob 仓库。
- 当运行需要附件挂载时，不复用旧会话容器，避免挂载状态串用。

这一阶段最重要的安全决定是“不猜编码、不自动解包、不把文件内容当指令”。附件能被读取，不等于附件可以改变 Agent 的系统规则。

### 阶段 7：会话压缩和存储生命周期

完成内容：

- 会话压缩时生成附件目录，保留 ID、文件名、媒体类型、状态、访问方式和已完成的派生表示。
- 租约保护运行中或资源读取中的附件。
- 删除先进入宽限期，再由垃圾回收执行物理删除。
- 回收前同时检查输入引用、租约和共享内容哈希。
- 完整性扫描识别记录缺失文件、大小不匹配、孤儿 Blob 和过期租约。
- “安全修复”只处理能确定不会破坏数据的过期租约和孤儿文件；缺失或大小异常只报告，不擅自重建。
- 上传和垃圾回收使用操作门控，避免同一物理对象被并发改写。
- 垃圾回收结果写入持久审计记录。
- 备份清单升级到 v2，备份和恢复都校验附件一致性。
- 恢复采用同盘临时目录和原子替换，降低中途失败留下半恢复状态的风险。
- 完整性和空间诊断通过 HTTP、Client 和 Desktop IPC 提供给设置页。

数据库和文件系统无法共享一个真正的事务。这里采用的办法不是假装它们能“一起提交”，而是通过暂存、原子重命名、可恢复状态、扫描和审计，让每个中间状态都有明确的恢复路径。

### 发布收口：把真实运行状态放进设置页

最后一轮没有扩展新的附件格式，而是做了一个小型发布收口。

设置页现在可以查看：

- 当前物理实际占用；
- 附件总数和可用数量；
- 唯一物理文件数量；
- 内容去重节省的逻辑空间；
- 当前可回收空间；
- 正在使用、正在导入、处理失败和过期占用；
- 最近扫描时间和存储健康状态；
- 安全修复和需要二次确认的立即回收操作。

视觉设计经过一次重要调整：实际占用和可回收空间可以作为同一个占用条上的两段，因为它们都属于当前物理空间；去重节省不能作为第三段塞进这根条里，因为它不是已经占用的磁盘空间。最终仍保留了空间关系的可视化，但没有用一个数学上误导的比例图。

设置页的修改操作不会只相信按钮请求成功。修复或清理完成后会重新扫描，以 Daemon 返回的事实作为最终显示；如果操作成功但复扫失败，界面会分别说明，避免把两个结果混成一句“成功”。

## 7. 支持矩阵

### 7.1 图片

当前主链路覆盖 PNG、JPEG、GIF、WebP 等常见安全图片格式；OCR 路由还识别 BMP。最终是否能原生发送，由“模型能力、供应商能力、当前媒体类型”共同决定。

| 情况 | 行为 |
| --- | --- |
| 模型支持图片，供应商也支持该格式 | 直接发送原生图片 |
| 模型不支持图片 | 提供附件资源提示，主 Agent 可调用本地 `ImageToText` |
| 模型能力未知 | 不冒险当作原生图片；按可用 OCR 降级处理 |
| 供应商适配器不支持图片 | 即使模型名称声称支持，也不能走原生图片 |
| OCR 工具或主机不可用 | 在请求供应商前阻止并说明缺少的能力 |
| 图片没有可见文字 | OCR 返回 `no_text_detected`，不生成场景描述 |

### 7.2 文本和代码

支持 `.txt`、`.md`、`.json`、`.csv`、`.xml`、`.yaml`、`.toml`、`.log` 及常见代码扩展名，但扩展名不是唯一依据，最终仍需通过内容和编码检查。

| 文件情况 | 行为 |
| --- | --- |
| 安全文本且不超过 16,000 字符 | 放入模型上下文，并加不可信数据边界 |
| 安全文本超过内联限制 | 提供最多 3,000 字符预览和只读资源 |
| 非法 UTF-8、无 BOM UTF-16、含 NUL 或异常控制字符 | 拒绝按文本读取 |
| 超大文本 | Agent 通过 `Read` 按行、分段读取 |

### 7.3 其他格式

PDF、DOCX、XLSX、PPTX、压缩包和未知二进制均不做自动转换，也不会作为乱码文本传给模型。错误发生在供应商调用之前，用户可以确定模型从未收到被拒绝的文件。

## 8. 关键决策及取舍

### 8.1 Daemon 拥有附件字节

选择：附件一旦上传，由 Daemon 管理不可变 Blob；会话和 UI 只保存稳定 ID。

收益：跨重启、分叉、重试和备份的身份稳定；减少本地路径泄露；服务端可以统一去重和清理。

代价：需要额外的上传 API、数据库状态和文件系统恢复逻辑。

### 8.2 文件资产和消息引用分离

选择：一个资产可以被多个输入引用，输入单独记录顺序。

收益：去重自然、历史语义明确、删除安全。

代价：查询和生命周期检查比“消息里放一个路径”复杂。

### 8.3 不兼容旧实验数据

选择：旧格式不自动迁移，检测后明确拒绝运行。

收益：避免长期维护尚未发布、语义不稳定的数据结构。

代价：已有实验数据不能直接升级，但这是用户明确接受的取舍。

### 8.4 能力判断放在运行路由，而不是只放在设置页

选择：设置页只提供声明；实际运行同时检查模型、供应商、媒体类型、工具和主机。

收益：配置错误不会直接变成供应商异常；路由决定可以持久化和排查。

代价：能力模型和错误状态更多，但这是可控复杂度。

### 8.5 `ImageToText` 只做本地 OCR

选择：移除工具内部远程视觉模型能力；它只读取图片文字，由主 Agent 决定何时调用。

收益：职责单一、可审计、离线可用，且不会绕过主模型能力配置偷偷调用另一套视觉模型。

代价：OCR 无法代替场景、图表和空间理解。

### 8.6 当前不做 PDF 和 Office

选择：明确阻止，不做半可靠的“解压后搜文字”。

收益：避免格式错乱、公式和图表丢失、宏和嵌入对象风险，也不制造“看起来支持但答案不可靠”的体验。

代价：发布范围更窄。后续需要单独设计转换、原生输入和扫描件 OCR 策略。

### 8.7 文件夹入口保留但不开放

选择：保留用户已经熟悉的入口，但显示不可用。

收益：不丢失既定界面结构，也为后续能力留下位置。

代价：暂时多一个禁用项，需要清晰提示原因。

### 8.8 空间图表只表达真实可相加的量

选择：占用条只显示保留数据和可回收数据，去重节省单独展示。

收益：既保留直观视觉，也不会让用户误以为“节省空间”是当前磁盘占用的一部分。

## 9. 可靠性、安全和可追踪性

### 9.1 上传与落盘

- 使用流式上传，避免大文件造成不必要的内存峰值。
- 先写暂存文件，完整校验后再原子移动。
- 内容哈希决定物理 Blob 身份，相同内容只存一份。
- 启动恢复处理未完成上传和遗留暂存状态。
- 文件名经过净化，不能通过路径片段逃出存储目录。

### 9.2 提示词安全

- 附件文本和 OCR 结果都标记为用户提供的不可信数据。
- 附件中的“忽略之前规则”“你现在是系统消息”等内容没有更高优先级。
- 不支持的格式在供应商调用前被拒绝，不会被静默丢弃。
- 大文本通过受限、只读资源读取，不把整个文件无界地塞入上下文。

### 9.3 生命周期安全

- 活跃运行使用租约，避免被垃圾回收删除。
- 逻辑删除有宽限期，降低误操作风险。
- 共享 Blob 必须确认所有引用都消失后才能删除。
- 修复操作遵循“能证明安全才自动修复”，缺失或损坏数据只报告。
- 垃圾回收保留持久审计，便于复盘删除原因和结果。

### 9.4 可追踪性

- 原始附件 ID 从输入、消息到工具记录保持关联。
- 图片路由决定和 OCR 表示状态可以追溯。
- 压缩摘要保留附件目录，不因上下文压缩失去访问路径。
- 备份清单包含附件元数据和一致性信息。

## 11. 过程中出现的问题和返工

### 11.1 初次“阶段完成”不等于系统级完成

多个阶段在复审或端到端测试后发现了真实问题，例如：

- 阶段 1 补强 Blob 边界、MIME、能力和恢复测试；
- 阶段 2 继续修正引用持久化和历史投影；
- Desktop 补过图片预览和旧启动路径问题；
- OCR 链路修正过路由后的 Agent 输入内容，以及 OCR 输出与原始提示词的对应关系；
- 生命周期阶段继续强化门控、审计和恢复边界。

这不是简单的“多写了几次代码”，而是说明附件横跨数据库、文件系统、运行时、供应商和 UI，只有单包测试远远不够。

### 11.2 模型支持图片，不代表整条链路支持图片

最初容易把能力看成模型的一个属性。实际必须同时满足：

```text
模型声明支持
  ∩ 供应商适配器能表达该输入
  ∩ 当前媒体类型被接受
  ∩ 所需工具或运行主机可用
```

任何一项不满足，都要走降级或阻止。这个认识最终形成了独立能力路由，而不是把判断散落在 UI 和各供应商适配器中。

### 11.3 数据库和文件系统的一致性比预期复杂

数据库事务不能回滚已经写到磁盘的文件，文件原子移动也不能自动提交数据库。因此增加了暂存状态、启动恢复、完整性扫描、修复、操作门控和审计。这些看似是“附件周边”，实际上决定了用户数据是否可信。

### 11.4 桌面异步流程容易串草稿

文件选择、上传进度、切换会话、取消、发送和 SSE 回包可能同时发生。只通过“当前会话”判断归属并不可靠。`draftId + taskId`、发送快照和服务端对账，是从实际竞态中沉淀出来的设计。

### 11.5 OCR 在源码里能跑，不代表打包后能跑

light-ocr 带有本地运行资源和原生依赖，Electron 又有 `asar` 打包边界。完整仓库测试发现并修复了运行时资源、解包和打包后 `createRequire` 命名冲突。发布前必须继续做真实安装包烟测。

### 11.6 第一版空间可视化表达不够准确

设计稿的可视化方向是对的，但把“去重节省”放进当前占用比例，会产生错误关系。实际页面一度又过度退化成纯数字表格。结合两者后，最终保留了占用条和层次感，同时把不可相加的指标拆开。

### 11.7 仓库级验证受环境噪音影响

- Node 版本不一致时，pnpm 可能尝试重建或清理依赖。
- Electron 运行中会锁定 DLL，强制安装可能触发 `EPERM`。
- Desktop 全量 lint 存在历史基线问题，因此本轮采用修改文件 lint 加全量类型检查和测试。
- 高并发全仓测试会触发现有时间敏感用例，最终用串行或分包方式确认真实结果。

后续发布脚本应固化已验证的 Node 和 pnpm 版本，并在构建前明确关闭正在运行的 Electron 进程，减少这些非代码噪音。

## 12. 做得好的地方

### 12.1 先定义语义，再做界面

附件先成为稳定资产和输入引用，之后 UI、OCR、资源读取、压缩和回收都围绕同一个身份工作。没有出现每加一种入口就重新发明一套附件结构的情况。

### 12.2 降级是显式、可审计的

模型不支持图片时，不会假装图片已经被理解；OCR 也不会伪装成视觉能力。未知能力、缺失工具和无文字图片都有明确状态。

### 12.3 主动收窄了不成熟格式

没有为了支持列表更长而粗糙解析 PDF、Office 或压缩包。这使当前发布承诺更可信，也给后续文档管线留下独立设计空间。

### 12.4 把文件系统故障当成正常场景设计

暂存、恢复、扫描、租约、宽限期、审计和原子恢复不是最后补丁，而是逐步成为主链路的一部分。

### 12.5 真实页面反馈进入最终设计

设置页没有机械照搬设计稿，也没有因为第一版实现简单就丢掉可视关系。最终把视觉层次与真实数据关系结合起来，这是发布收口应有的方式。

## 13. 可以改进的地方

### 13.1 阶段验收可以更早加入跨包场景

部分问题直到全仓或打包测试才出现。以后每个跨层阶段都应至少保留一条从 UI 或 Client 到 Daemon、再到持久化结果的纵向测试，减少阶段末集中返工。

### 13.2 能力矩阵应更早成为单一文档

图片原生输入、OCR、文本资源和不支持格式在不同阶段逐步形成。如果一开始就维护一张“文件类型 × 模型能力 × 供应商能力 × 工具可用性”的决策表，会更容易发现空白状态。

### 13.3 打包验证需要进入常规门禁

OCR 的问题证明，包含原生依赖和运行时资源的功能不能只靠单元测试。后续应把安装包启动、OCR 一次、资源读取一次作为发布前固定烟测。

### 13.4 视觉验收环境需要更稳定

自动化视觉工具认证超时，使最终调整更依赖人工反馈。可以补一个稳定的本地演示数据入口或 Storybook 场景，让空间页在没有真实大量附件时也能可靠验证各种状态。

### 13.5 阶段文档和提交命名可以更统一

这次阶段很多、复审提交也多。后续可以在每个阶段文档顶部固定记录目标、非目标、关键提交、最终验证和遗留事项，减少最终复盘时重新拼接上下文的成本。

### 发布前仍需确认

- 用户对设置页最终真实页面做最后一次视觉确认。
- 用正式打包产物完成一次图片原生输入、OCR、文本资源和不支持格式阻止的烟测。

- 当前功能仍在 `codex/attachment-release-closeout` 分支，尚未合并回 `main`。

### 已知产品边界

- OCR 只能提取文字，不能代替通用视觉理解。
- 当前没有用户级配额配置、容量告警和完整附件管理器。
- 历史消息编辑时不能替换附件集合。
- 文件夹上传尚未定义实时引用还是快照语义。
- 旧实验数据不迁移，这是已接受的兼容边界。

### 后续技术能力

- 分片和断点续传，以及弱网络、远程客户端上传恢复。
- PDF / Office 的转换、原生文档输入、扫描件 OCR 和页面级引用。
- 供应商 Files API 缓存、凭据作用域、过期、删除和重试。
- 恶意文件扫描、隔离区和转换进程沙箱。
- 更完整的指标、链路追踪、故障注入和容量告警。

## 15. 推荐的后续路线

### P0：先发布和观察

建议现在停止继续扩文件类型，先完成下面四件事：

1. 完成设置页视觉验收。
2. 在本地把功能分支合并回 `main`。
3. 跑正式安装包烟测，尤其验证 OCR 运行资源和关闭附件功能的路径。
4. 发布一份清晰的支持矩阵和限制说明。

这是当前投入产出最高的下一步。核心链路已经足够完整，继续加格式会让发布节点不断后移。

### P1：只有远程或大文件需求明确时，再做断点续传

如果近期用户主要在本地上传几 MB 到几十 MB 的截图和文本，现有流式上传已经够用。只有真实出现弱网络、远程 Daemon 或百 MB 文件频繁失败时，再启动分片上传阶段。

### P2：把文档格式作为独立项目

PDF 和 Office 不应简单追加到文本分类器。建议单独确定：

- 哪些格式走供应商原生文档输入；
- 哪些格式本地转换；
- 如何保留页码、工作表、幻灯片、表格和图片关系；
- 扫描 PDF 何时进入 OCR；
- 转换结果如何缓存、引用和失效；
- 失败时如何让用户知道模型实际看到了什么。

### P3：再补企业级治理

当附件用于更广泛来源或共享环境时，再增加恶意文件扫描、隔离、细粒度配额、指标、告警和故障注入。它们不是当前本地发布的阻塞项，但会成为多人和远程部署的必要条件。

## 16. 可复用的工程经验

1. 附件不是消息上的一个 URL，而是有身份、状态、引用和生命周期的数据资产。
2. 输入和附件引用必须一起接纳，不能靠事后补写消息投影。
3. 多模态能力等于模型、供应商、媒体类型和运行环境的交集。
4. “未知”不能偷偷等同于“支持”；降级必须显式并可追踪。
5. OCR 是文字提取工具，不是低配视觉模型。
6. 文件内容永远是用户数据，不因为被放进附件就成为系统指令。
7. 数据库和文件系统之间必须为中间状态设计恢复路径。
8. 自动清理只能处理能证明安全的对象；不确定的数据应该报告而不是猜测修复。
9. UI 图表必须表达真实关系，不能只因为数字都和空间有关就塞进同一比例条。
10. 跨数据库、文件系统、原生依赖和桌面打包的功能，必须通过全仓测试和真实产物烟测才能完成。

> 状态：提案，产品范围已由用户确认；按 Ponytail 复杂度审核收缩，尚未实施。

## 1. 目标与本次边界

先修复三个前置问题，再让主聊天与侧聊支持运行中补充。完全访问默认直接补充，询问审批和自动审查默认排队，允许手动切换。本轮仅修订文档，不修改业务代码。

Run 是一次任务执行，内部可能连续请求多次模型、调用多个工具。“现在补充”交给当前 Run 在后续可处理的位置使用；“结束后执行”保存为独立 Run，进入现有队列。

本次交付包括停止不受消费等待阻挡、审批使用最新已应用人工指令、输出要求检查、精确目标、发送选择、主聊和侧聊共用队列，以及可靠重试。生成抢占、队列编辑与重排、停止后发送、自动恢复旧任务均另行立项。

## 4. 产品规则

### 4.1 默认值与手动选择

| 条件 | 默认行为 |
| --- | --- |
| 无当前 Run | 正常发送并启动新 Run；请求仍采用 queue |
| full_access，当前输入可补充 | 现在补充 |
| ask 或 auto_review | 结束后执行 |
| 当前输入明确不支持补充 | 结束后执行，提交前说明原因 |

默认只按授权档位决定。plan 不额外改变此映射；full_access + plan 默认补充，原有计划模式限制继续生效。

输入框只有“现在补充”“结束后执行”两个选项。主聊天和每个侧聊独立持有当前选择，不写设置、草稿或恢复文件。用户手动切换只影响本条消息；接纳成功后恢复为当前权限默认值。切换聊天或关闭侧聊也重置。

发送前改变授权时，尚未手动选择的输入随默认值更新，已经手动选择的本条消息保持选择。提交后固定 inputId、正文、附件、delivery 和 expectedActiveRunId；重试不得重新按当前模式计算。发送结果未知时先核对 inputId，不自动生成新请求。

### 4.2 交互

- 有内容时显示真实发送按钮：运行中为“补充当前任务”或“加入队列”，空闲为“发送”；停止独立显示并作用于当前作用域的指定 Run。
- Enter 与点击使用同一提交函数，保留 Shift+Enter、输入法确认和焦点操作。停止请求在途时禁止同一作用域提交，其他会话不受影响。
- 收到输入接纳事件后，沿现有状态同步清理本次准确草稿、释放发送状态并恢复默认选择；HTTP 仍可继续等待。迟到的响应不能清空后续新草稿或把确认状态改回失败。
- 补充的提示为“在当前步骤结束后处理，不会撤销已经开始的操作”。普通补充不替代审批或问题卡片的回答。
- 普通队列保留提升和取消。直接补充接纳后不增加单条撤回接口，用户可停止当前 Run。

### 4.3 输入限制

附件、需要单独装配的插件能力或上下文、观察授权、outputSchema 等继续由服务端检查。客户端对已知限制显示原因，并将不支持的“现在补充”禁用；不能放宽服务端规则。

新版 Desktop 的有目标补充遇到不兼容输入时，服务端在接纳前拒绝，不静默转为排队。保留草稿，用户选择“结束后执行”后作为新提交发送。历史调用方未使用新目标保护时维持原接口规则，不为本次 UI 需求统一更改全部调用方的行为。

## 5. 最小数据与应用事实

不新增数据库列、表或逐输入状态机。新增信息放入现有宿主 metadata，并明确拒绝调用方伪造：

| 信息 | 保存位置 | 用途 |
| --- | --- | --- |
| 新版直接补充绑定的目标 | `Input.metadata.steerTargetRunId` | 接纳后知道输入交给哪个 Run；初次写入时固定 |
| 提升中的目标与原队列身份 | 原 queued Run 的 `metadata.promotion` | 复用已有关系；增加 kind=steering，成功后仍用既有 kind=steered |
| 真正应用的有序输入 | 目标 Run 的 `metadata.appliedInputState: {revision, inputIds}` | 审批唯一应用依据，UI 也从这里判断是否加入上下文 |
| 无法继续的原因 | 原有 Run 终态、error 与提升失败路径 | 不再保存一份逐输入 failed/cancelled 状态 |

promotion 继续使用已有 inputId、queuedRunId、activeRunId 等字段。kind=steering 表示运行器已经占位，原 queued Run 仍不可独立派发；拒收时恢复原队位和原 metadata，成功后保留既有 interrupted＋promotion 审计记录。取消由既有 Run 状态表达，不再增加 promotion 的取消状态。

Input.delivery 保留初始意图，提升的实际路由从 promotion 得到，不复制 requested/effective 两个字段。应用版本只归 Run，用于审批；客户端不新增逐输入比较版本。

### 5.1 真实应用边界

保留运行事实 `input.applied`，负载为 `{inputIds, revision}`。Core 在内容准备成功并写入运行历史后调用 `markInputsApplied(inputIds)`；运行器验证这些 ID 属于本 Run，发布事实。宿主保存成功后才更新本地序列并继续模型请求。失败则不继续派发。

原 `input.accepted` 不改称 applied；它和用户消息投影都不能单独证明模型历史已使用输入。自定义执行器没有应用证明时，不能获得自动审批的推定授权。

宿主通过已有 Run 更新事务保存应用序列并发布 `session.run.updated`。若输入来自提升，在同一事务内结算原 queued Run 和 promotion。无需新建 `session.input.delivery.updated` 事件或逐输入全记录广播。

### 5.2 界面状态从现有记录计算

| 证据 | 显示 |
| --- | --- |
| 本地提交尚未被输入列表确认 | 正在发送，沿用既有 submission.phase |
| 独立 queued Run 待执行 | 等待前一任务结束 |
| 直接补充目标或提升目标存在，但 inputId 尚不在其应用序列 | 等待当前步骤结束 |
| inputId 已在目标 Run 的应用序列 | 已加入上下文；与正式消息合并展示 |
| 目标终态且 inputId 未应用 | 尚未应用即结束；沿用 Run 错误或停止原因 |

“已加入上下文”不等于供应商收到、模型理解或任务完成。旧 Run 没有应用序列时保留旧显示，不根据用户消息反推新事实。

权威状态继续只由现有事件流和快照写入，沿用 seq、快照游标与同步顺序；RPC 仅确认调用结果，不把旧响应中的 Run/Input 再覆盖进 store。侧聊沿自身订阅得到同一判断，不另建订阅或记录副本。

## 6. 三个前置修复

### 6.1 消费等待在会话操作通道外

```ts
const prepared = await operationRunner.run(sessionId, async () => {
  // 校验、保存并登记投递；返回对象，不直接返回消费 Promise。
  return { completion: registerInput() };
});
return await prepared.completion;
```

复用现有返回类型推断，不增加通用 PreparedPromptOperation 抽象。长内容准备在短操作外完成，登记前复核配置和目标；短操作内不等模型、审批、工具或输入消费。

提升必须先从可派发队列移出并在现有 promotions 中占位，再释放通道。完成与失败回调仍受原 owner、queuedRunId、目标 Run 和取消状态约束；只在短操作内结算，不持锁等待。shutdown 必须收束所有 Promise。

### 6.2 审批使用已应用人工指令

- 原始 scope.inputId 和 Run.inputId 保持运行归属；另由运行器提供只读已应用序列，effect 携带宿主生成的快照。
- 宿主核对快照与当前 Run 记录一致，验证会话、应用事实和人工来源。其他会话、未来队列、插件、Goal 自动提示和子 Agent 报告不能成为人工授权。
- reviewer 当前指令取最后一个已应用的直接人工输入，历史包含更早的人工历史和同一 Run 已应用补充，去重后保留实际应用顺序。不能只按最初输入的 seq 截断，也不能简单取最大 seq。
- 每次审查记录应用版本，在审查前、结果结算前及实际工具调用前核对。版本变化时阻止该次调用，让模型重新判断；不自动重做工具，也不把 Run 初始版本永久绑定所有后续调用。
- 保留敏感信息过滤、长度限制、引用不授权与人工回退。完整保留最新限制，不能为了截短历史而删除撤销。
- 尚未应用的补充不构成新授权，不自动取消在途工具或审批；不引入“等补充应用才能结束工具、又等工具结束才能应用补充”的循环等待。

### 6.3 输出要求不得通过提升绕过

Input 或 queued Run 任一保存了 outputSchema，或两份保存值冲突，一律在移队列、调用运行器前拒绝提升。原记录、队位和输出要求不变。直接 steer 的既有禁止继续保留，不支持运行中协商或更换合同。

## 7. 后台、协议与恢复接线

继续使用现有路由和 HTTP 回执：接纳消息先发布 `session.input.admitted`，消费结果在通道外等待；HTTP 不统一改成“登记后立即返回”。UI 依靠接纳事件或快照释放等待，连接中断则沿 inputId 核对。

精确协议保持 7。新增可选 expectedActiveRunId，并通过 `features.steer=2` 表明支持该字段及绑定保护。新版 Desktop 的运行中补充必须带它；Client 发送前检查能力。旧调用不带该字段时保留原合同，不增加第二套 route；queue 请求不携带它。

同 ID 重试先核对原请求，不能因当前 Run 已结束就重新执行。只对新接纳请求检查当前目标：写入前目标不匹配返回 409；登记阶段拒收或接纳后目标不再接收时，用现有失败收束记录结果，不能静默改投后一个 Run 或创建替代执行。新目标保护必须在 runtime 的同步登记点生效，不能仅在 HTTP 入口比较。

明确拒绝且确认未接纳的消息，可以恢复为草稿，由用户按当前目标重新提交并生成新 inputId；这与“核对后重试原请求”分开。网络结果未知时不得直接生成新 ID 重发。

目标与人工应用字段由宿主生成并列为保留 metadata。fork 复制历史时沿现有宿主字段清理去掉活体 steerTargetRunId，不让新会话继承旧 Run 的执行目标。memory 会话仍不写 SQLite 或恢复文件。

启动恢复继续中断旧 active/pending Run、收束孤儿输入和过期审批，不自动恢复执行。已应用序列保留审计事实；未应用输入根据目标与原有终态显示失败或停止，不另跑一套恢复状态机。停止指定 Run 和会话级停止的既有范围均不改变。

## 8. 主聊天与侧聊

默认值和当前本条选择用一个小函数或现有 hook 计算，放在输入框分类；不新增配置服务或偏好持久化。提交后 main/preload 只校验并透传 delivery 和目标，不重新读取当前权限计算发送方式。

两处共用 PendingPromptQueue 和既有 draft/submission 恢复。为 promoteQueuedPrompt、cancelQueuedPrompt 增加可选 target，复用 SubmitPromptOptions.target；整个异步操作捕获同一 sessionId/view，不在 await 后用 activeSessionId 决定归属。主聊未传 target 的行为保持原样。

侧聊必须接通输入接纳确认、准确草稿清理、等待状态、提升、取消与失败核对；切换或关闭后到达的旧回执不能修改新目标或主聊天。直接补充的等待提示从目标 Run 应用序列计算，不能因 accepted 消息出现就显示“已处理”。

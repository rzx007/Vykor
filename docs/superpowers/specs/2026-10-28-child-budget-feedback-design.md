# 子代理预算提示与未完成结果处理方案

> 状态：待审阅，尚未实施。核对日期：2026-10-28。本文只规定预算提示、结果交付和桌面展示，不改变已有预算上限，不增加自动续跑。

子代理达到运行上限后，应保留真实的未完成状态，把已经取得的结果和停止原因交给主代理，并在界面中说明用户接下来可以做什么。单独显示红色“失败”，会让用户误以为构建失败、没有取得任何结果，或者需要自己理解内部异常。

本方案沿用现有运行记录和工具入口，补齐三处：运行前明确可用轮次，结束后提供可处理的结果说明，界面区分预算耗尽与执行错误。

## 一 问题现象

### 任务背景

用户要求修复一个 Three.js 池塘页面的四处问题：水面颜色发灰、鱼缺少水下感、夜间页面底部露白，以及季节按钮图标与实际循环切换行为不一致。

主代理修改页面后，把“运行生产构建并检查修改是否正确”交给验证子代理，明确要求子代理只检查、不编辑文件；浏览器中的实际外观由主代理自行检查。创建验证子代理时，主代理显式设置 `maxTurns: 5`。

这里的“轮次”指模型生成及其后续工具调用的一次循环，不是执行秒数，也不是用户发送消息的条数。现有实现会把最后一次请求留给无工具收尾，因此该预算最多允许 4 次普通请求，再生成一次部分报告。

### 实际执行过程

以下为已观察到的一次完整过程，其他同事不需要访问原会话即可据此理解和构造回归场景。

| 顺序 | 记录 |
| --- | --- |
| 1 | 子代理检查项目目录和配置。其中的 `git diff` 命令出错，该工作目录未提供可用的 Git 仓库比较环境 |
| 2 | 子代理读取 JavaScript、CSS 和 HTML 源码，工具返回的正文较长，出现截断及补读提示 |
| 3 | 子代理执行生产构建，退出码为 0。构建工具提示产物体积偏大，该提示没有使构建失败 |
| 4 | 子代理继续读取源码并执行 `node --check src/main.js`，语法检查退出码为 0；源码正文再次出现截断提示 |
| 5 | 第 5 次请求进入无工具收尾，子代理报告构建与语法检查通过，但进一步运行检查尚未完成，报告以 `VERDICT: PARTIAL` 结束 |
| 6 | 运行按预算规则结束，状态为 `failed`，错误为 `Exceeded maximum agentic turns (5)`，分类为 `failureKind: max_turns`；收尾报告保存在 `partialResult` 中 |
| 7 | 主代理调用 `JobWait`，正常取得失败状态和部分报告；随后说明构建与语法检查通过，并结束自己的回复，没有解释委派验证仍有未完成事项 |

子代理已经取得了可用结果：生产构建和 JavaScript 语法检查通过。它没有确认具体正确性缺陷，也没有完成原先计划的针对性运行探测，因此不能把这些通过项等同于全部验证通过。

### 用户看到的问题

会话中的子代理活动行显示任务名称、红色“失败”和耗时，没有直接说明是轮次预算用完，也没有说明已有部分结果。任务详情使用失败提示展示错误；错误字段可能包含整段部分报告，造成成功检查项和技术错误混在同一块错误提示中。

与此同时，主代理回复只强调“构建和语法检查通过”。用户需要自己判断：到底是程序坏了、构建失败了，还是验证代理没有完成剩余检查；也无法从卡片直接知道已经保留什么、下一步由谁处理。

需要解决的是三个信息缺口：子代理在普通工作阶段缺少清晰的剩余轮次预期；主代理拿到失败与部分结果后缺少明确的处理建议；界面把预算耗尽统一展示成普通执行失败。

该过程中的 `JobWait` 已经正常返回，主代理也在子代理结束之后才结束。本文不把它归因为等待工具受阻或子代理结果丢失；历史图片恢复问题独立处理。

## 二 当前机制与开源 Codex 参考

### 当前项目已有的能力

- `QueryEngine` 对子运行应用宿主固定的 `hardMaxTurns`。模型、请求配置或后续输入不能突破该次运行的上限。
- 最后一次模型请求已经预留给无工具收尾。因此 5 轮上限最多容纳 4 次普通请求和 1 次收尾请求；普通请求可以包含一组工具调用。
- 预留的收尾请求即使生成了报告，也不被当作成功完成。运行仍保留 `max_turns` 原因，报告进入 `partialResult`。
- `JobRead` 和 `JobWait` 可以取得失败原因、部分报告和状态；`JobSend` 能在现有授权和预算限制内给可接收输入的子代理继续分派工作。
- 桌面会话内的活动行、侧栏任务列表和详情页主要按 `task.status` 展示。预算耗尽和普通执行错误都显示为“失败”。详情还可能把整个部分报告当作错误正文再次展示。

需要补的是预算预期和结果解释，不是再做一套收尾请求、任务状态机或后台调度器。

## 三 方案选择与范围

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 只修改界面文案 | 改动最少 | 子代理仍不知道可用轮次，主代理仍缺少明确的续做提示 |
| 保留现有执行规则，补预算提示、结构化结果说明和统一展示 | 能改善预算使用和结果理解；不引入新调度状态 | 需要同时覆盖 Core、Jobs 工具和桌面三个入口 |
| 自动扩大预算并续跑 | 部分任务可以自动完成 | 容易绕过限制、重复被阻断的操作，且需要新的累计预算和停止规则 |

采用第二种方案。实施范围如下：

1. 对已经设置硬轮次上限的子运行，在每次普通模型请求前提示剩余次数和收尾预留。
2. 在 `JobRead`、`JobWait` 返回中增加明确的未完成原因和处理建议；实时与归档读取保持一致。
3. 会话活动行、任务列表、任务详情使用同一套预算状态解释。
4. 调整父代理可见的 `Agent.maxTurns` 参数说明，让它知道上限包含收尾请求。

本次不调整默认预算、不删除现有异常、不自动续跑、不增加全局 token 预算、不强制父代理等待全部后台任务，也不提供新的子代理直接聊天入口。已有权限、审批和工具安全限制继续生效。

## 四 运行流程与状态归属

### 创建和执行

入口仍为 `Agent` 工具。有效轮次上限沿用 `resolveChildMaxTurns` 的现有计算规则，调用方只能收紧配置上限。

每次普通模型请求前，Core 根据本次运行已经使用的请求次数计算剩余额度，在当次请求的系统提示中追加简短说明：

> 本次委派还可使用 5 次模型请求，其中最后 1 次仅用于总结。请在此前完成必要检查，优先使用针对性读取；最终说明已验证、未验证和受阻事项。

下一次请求中的剩余额度更新为 4，以此类推。该提示由运行时计算，不接受模型填写的剩余次数，不逐轮追加到长期历史。

当 `hardMaxTurns` 未设置时，不显示虚构的剩余次数。上限为 1 时，明确只有收尾请求，没有普通工具执行额度。工具调用失败、输出截断后的补读仍消耗普通请求次数，提示不承诺某个固定轮次必然够用。

最后一次请求沿用已有的无工具收尾，不能额外再申请一次模型请求。自然提前完成仍按正常成功处理；进入预算收尾后仍按未完成处理，不根据报告中的 PASS 等自由文本更改终态。

轮次计算和提示只存在本次 Core 查询循环中。真实运行结果、失败分类和部分报告继续由现有子运行保存，daemon 继续负责持久记录与界面更新。

### 结果交给主代理

入口仍为 `JobRead` 和 `JobWait`。工具返回原有的快照、原始输出、`failureKind` 和 `partialResult`，并补充结构化结果解释。建议字段名为 `outcome`，表示业务完成情况，不替代现有 `snapshot.status`：

```json
{
  "outcome": {
    "status": "incomplete",
    "reason": "max_turns",
    "hasPartialResult": true,
    "nextAction": "先阅读部分报告，区分已完成与未完成事项。若仍需继续，确认没有权限或工具阻碍后，在现有授权和预算范围内继续分派剩余工作；不要重复已完成的检查。"
  }
}
```

处理规则：

- 只有终态为失败且带有明确预算原因的子运行才解释为 `incomplete`。`max_turns` 与子运行的执行时限 `timeout` 分开保留原因。
- 普通执行错误解释为 `failed`；不因为存在部分文本就改成预算耗尽。
- 等待调用超时而子代理仍运行时，只保留 `timedOut: true` 和运行中状态，不生成未完成终态。
- 实时和归档快照的失败元数据位置不同，应在工具输出边界归一化；同一个 runId 返回相同解释。
- 若部分输出被裁剪，`hasPartialResult` 仍按对应运行保存的结构判断，不按当前正文长度判断；继续保留游标和补读能力。
- `nextAction` 根据目标是否还能接收输入区分继续原子代理和重新分派；不能提示对只读归档执行 `JobSend`。
- 文案只提示主代理决策，不自动执行 `JobSend`、创建替代代理或承诺会自动恢复。

一次新的续做运行仍受自身有效上限和现有共享限制约束，不扩展已经结束的那一轮，不继承上一轮的成功结论。若再次失败，仍保留对应 runId 的独立原因和部分结果。

### 主代理如何解释结果

工具说明和结果建议共同引导主代理：任务尚有未完成验收时，不能仅把已通过的构建等同于整体验证完成。它应结合部分报告，决定自己接手、继续分派，或说明目前停止在哪一步。

对本次实例，建议主代理的用户回复包含：

> 生产构建与 JavaScript 语法检查通过。独立验证代理已达本次运行上限，进一步运行检查尚未完成；已保留部分检查结果。

这是一条处理指导，不是通过匹配自然语言保证父模型一定遵循的程序约束。自动续跑和自动唤醒空闲父代理均不纳入此次实现。

## 五 桌面展示

后端继续保留现有 `failed` 状态和真实错误。桌面根据该任务的结构化 `childFailure.failureKind` 派生展示状态，不做数据库迁移，不用异常字符串或报告中的 PASS、FAIL、PARTIAL 推断状态。

| 真实情况 | 活动行及列表状态 | 详情说明 |
| --- | --- | --- |
| 轮次耗尽 | 未完成 · 已达轮次上限 | 本次可用轮次已用完，剩余工作尚未完成 |
| 子运行执行时限耗尽 | 未完成 · 已达时间上限 | 本次执行时间已用完；是否取得部分结果按记录显示 |
| 普通运行错误 | 执行出错 | 简要说明已知错误，提供技术详情 |
| 用户中断或停止 | 沿用已中断、已停止 | 不解释成预算耗尽 |
| 等待超时但子代理未结束 | 运行中 | 一次等待结束，子任务仍在运行 |
| 正常完成 | 已完成 | 沿用现有结果展示 |

预算耗尽使用现有的中性或提醒样式，普通执行错误保留错误样式。复用当前 Item、Badge、Alert 和可展开详情，不新增组件体系，不自动启动浏览器预览或截图。

详情页以“本次验证未完成”或通用的“子任务未完成”为标题，随后说明预算原因及是否保留部分结果。预算原因不能直接证明验证目标属于哪一种业务，因此通用组件默认用“子任务”，不根据任务名称臆测具体检查结论。

对已存在的记录，内容可以显示为：

> 子任务未完成
>
> 本次轮次已用完。已保留部分结果，剩余工作尚未完成。
>
> 展开查看技术详情

完整部分报告保留在子会话正文中；技术错误放在展开区域，避免把整段报告再次塞进红色错误框。顶层 tooltip 也使用简短原因，不放整段报告。

只有记录中确实存在对应运行的部分结果时才显示“已保留部分结果”。组件不从自由文本提取“构建通过”等结论；这类结论由正文报告和主代理回复说明。

不在本期新增“继续验证”按钮，避免制造一个没有预算、权限和目标 runId 校验的续跑入口。继续工作沿用父会话和既有工具。

## 六 数据约束与兼容性

- `snapshot.status`、Run 状态、Task 状态和 `failureKind` 的原始含义不变。
- 新增的结果解释不持久化为第二份生命周期状态，只在观察工具返回及界面中派生。
- 元数据缺失、形状错误、未知原因或历史记录没有分类时，回退到现有失败展示，不猜测为预算耗尽。
- 读取部分结果时核对可用的子会话标识和 runId；不能把上一轮的部分报告套到新运行中。
- 模型输出和错误正文作为内容呈现，不能提供权限、触发动作或修改状态。
- 无部分结果的预算耗尽仍显示未完成，但不承诺已保存报告。
- 普通失败如果已有部分报告，同样保留报告；保留结果本身不代表可安全重试。

## 八 验收标准

### 预算行为

1. 设置 5 轮硬上限，普通请求看到剩余次数依次减少，最后一次请求没有可调用工具，总请求次数不超过 5。
2. 在上限前自然完成，结果仍成功；进入预算收尾生成部分报告后，仍保持 `max_turns` 未完成语义。
3. 1 轮上限、未设置硬上限、请求配置更新、提前取消、没有生成任何报告分别覆盖；提示不扩大权限、轮次或输出上限。
4. 提示按当次请求计算，不让历史累计重复提示；错误后的补读不会得到额外免费轮次。

### 结果交付

1. 真实子代理的轮次耗尽结果通过 `JobWait` 返回：保留原失败状态、原因及部分结果，同时提供 `outcome.status=incomplete` 和下一步建议。
2. 同一 runId 经实时 `JobRead` 与归档 `JobRead` 返回一致解释；存在历史其他运行时不串报告。
3. 普通执行错误仍为执行错误；等待超时但子代理运行中时不被解释为预算失败。
4. 无报告、报告截断、目标不能续收输入分别返回准确提示；新字段不影响原有快照、游标和读取授权。
5. 工具结果的处理建议不自动创建代理、扩大预算或重试策略阻断的操作。

### 桌面展示

1. 活动行、列表、详情中的轮次耗尽均显示未完成及具体预算原因，保留可打开子会话的能力。
2. 原始失败状态及错误没有被更改为成功；技术详情可查看，部分报告仍保留在正文中。
3. 普通执行错误继续使用错误展示，用户中断、停止和等待中的状态不被误分类。
4. 不解析模型自由文本决定颜色或完成状态；错误或缺失的元数据不导致组件崩溃。
5. 提供存在和不存在部分结果的行为测试，以及一次运行完成后下一次运行继续更新的状态测试。

实施时先写失败测试，再修改实现。完成后运行相关 Core、Jobs、桌面测试及类型检查，并执行 `pnpm check:retired-ui` 和 `pnpm check-docs`。样式由用户在实际界面查看反馈。

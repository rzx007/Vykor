# 工具管理与执行

处理工具从注册、向模型展示，到检查参数、获取权限、执行和返回结果的完整过程。

| 文件 | 用途 |
| --- | --- |
| `tool-registry.ts` | 保存工具定义、校验注册，按可见范围生成运行和模型使用的工具集合 |
| `tool-discovery.ts` | 在本次运行内发现和启用工具 |
| `tool-definition-identity.ts` | 为同一工具定义提供稳定标记，供绑定和授权校验使用 |
| `tool-input-schema.ts` | 规范工具输入并按参数定义检查 |
| `tool-input-reuse.ts` | 从历史成功调用中复用允许复用的输入 |
| `query-tool-preparation.ts` | 解析和检查输入，区分可执行调用与应直接返回的错误 |
| `query-tool-permissions.ts` | 处理权限、执行前后的回调，以及工具状态事件 |
| `query-tool-limits.ts` | 工具超时和输出大小限制 |
| `tool-execution-context.ts` | 为工具组装当前执行环境与可见工具集合 |
| `tool-permission-request.ts` | 工具内部具体操作的统一权限入口，按当前运行绑定检查并决定是否需要宿主审批 |
| `checked-tool-execution.ts` | `executeCheckedTools()` 串联准备、授权、分组执行和结果交付 |
| `tool-failure-memory.ts` | 记录失败输入和证据版本，识别未发生变化的重复失败 |
| `tool-batch-recovery.ts` | 完整批次交付后，计算纠错次数、恢复额度和是否要求模型收尾；额度耗尽时抛出现有错误 |
| `tool-result-feedback.ts` | 将执行结果、失败提示和文件事实整理成模型可读取的内容 |
| `__test__/` | 上述规则与引擎中的工具执行集成测试 |

`QueryEngine` 将模型生成的工具调用交给 `executeCheckedTools()`。输入检查通过后才进行授权与执行，输出结果返回引擎写入消息历史，供下一轮模型使用。

工具内部的 `ToolContext.requestPermission` 及工具可见的 `agent.effects.requestPermission` 也先经过同一个权限检查器，不再直接透传到宿主。当前运行必须包含请求目标，来源和参数定义取自捕获绑定；完全访问在禁止规则检查后直接批准，拒绝直接返回，普通具体操作确认才交给宿主持久审批。外层与内部审批共用 `requestPermissionDecision()` 发布请求和结果事件。具体确认带宿主生成的 `confirmation: once`，不能被工具级会话授权复用或升级为会话授权。输入在检查前复制；执行器在单次工具超时控制器建立后，把两条权限入口绑定到本次调用信号，取消或超时会使等待审批过期，迟到批准不能继续执行。真正的 `askUserPrompt` 保持独立。

受检执行返回两条独立通道：`results` 保存每个工具的结果，`fatalFailure` 只保存无法可靠继续运行的宿主或运行错误。超时、工具普通抛错和 `unknown` 结果不进入致命通道；错误、已有输出和恢复提示写入历史后交给模型继续处理。SDK 的 `executeTool()` 和嵌套 `invokeTool()` 也返回这些工具错误，仅在致命失败时抛出。运行限额、结果正文保存失败、调用跟踪失败或生命周期交付失败仍在完整结果交付后传播。模型循环收到运行取消后停止请求；SDK 显式调用仍按原契约返回 `interrupted` 错误结果。

创建工具上下文时，执行器传入宿主致命失败上报能力和启动门禁。嵌套受检执行通过 `onFatalFailure` 连接父调用，在保存错误、调用跟踪或生命周期交付失败时立即上报，不依赖代理工具是否捕获了异常。`dispatchSignal` 只控制新调用的启动，不取消已经开始的调用；代理捕获故障后再次调用工具也不能绕过父门禁。这些能力仅在执行器之间传递，不从工具返回数据中读取；父批次停止尚未启动的调用，已开始的调用仍等待实际结束。

批次结果全部写入历史并交付 `tool_use_end` 后，引擎先检查执行失败、取消和成功结束运行的内部工具，再调用 `decideToolBatchRecovery()`。它先检查参数与文件条件的纠错上限，再通过回调观察轨迹，最后检查重复失败的恢复额度；纠错已达上限时不观察轨迹，恢复额度耗尽时仍观察本批结果。成功与失败混合批次可以解除重复失败恢复，但只有全部成功才清零两类纠错次数。计数和剩余额度仍由本次 `submitMessage()` 保存，普通函数只返回下一轮状态或抛出错误；逐条失败记忆、证据版本和结果保存留在引擎原位置。`__test__/tool-batch-recovery.test.ts` 覆盖这些顺序边界。

参数别名只在工具顶层识别，例如把 `filePath` 对应到 `file_path`；嵌套对象和数组项作为业务 JSON 按声明检查，不推断别名。结构化交付中的 `data.path` 与允许的额外字段 `data.file_path` 可以分别表示来源和目的路径，不能因此被误判为同一个参数。

`ToolContext.toolResults` 是宿主已按当前 Run 和工具来源绑定的异步结果读取能力，供内置 `ToolResult` 查询使用。旧的同步 `readToolResult()` 仍只读取当前 Run 中有限大小的结果，并核对原插件来源和捕获的执行函数，不转为跨 Run 全库访问。`tool-result-feedback.ts` 生成的补读提示在正文预算处理后添加，自由工具元数据不能伪造引用。

普通权限与审批通过后，执行入口调用当前 Run 的 `checkToolDispatch`，核对 owner、会话、Run、输入归属、cwd、最终工具绑定和运行修订。校验用的 cwd 取可信环境的宿主目录；工具自身仍收到环境内执行目录，二者在 WSL 等环境可以不同。检查失败终止本 Run；工具普通错误与 unknown 只反馈本次调用，不限制其他新调用，也不自动重试。实际调用 Promise 一直跟踪到工具真正结束。

合法返回的成功和错误都补齐 `completed`；已经调用却声称 `not_started` 的结果按 unknown 反馈。可信内置文件工具因新项目规则而在修改前停止时，保留经受检入口确认的 `not_started` 条件失败。只对完成结果保存正文，保存成功后才发布补读引用；保存失败交付原事实并报告宿主错误，不伪造引用。超时后迟到结果仅完成调用收尾，不补写正文或二次交付。

`project-instructions.ts` 为每个模型工具批次建立 `projectInstructionState()`，通过 `ToolContext.projectInstructions` 给可信内置工具提供额外规则文件的普通 Read 权限检查和三态去重。状态不跨批次保存在常驻集合：历史中同时带受检宿主版本键和完整规则片段首尾标记才视为已交付；同批次共用的临时集合仅表示等待交付。普通文件正文或插件 metadata 伪造标记不会抑制规则。microcompact 清空或 context collapse 截短工具正文时移除其可信版本键，即使头尾标记碰巧保留也必须重新注入。宿主标记的规则片段有独立上限，不被普通工具结果预览剪断。实际目录发现、简单分片和有界读取归 tools/file 的单一 helper，执行器不另造扫描器。历史外 SDK `executeTool()` 不建立模型已阅状态，保留独立受检调用的原契约。

引擎先一次性准备实际进入模型历史的格式化、预算后正文，再调用 `projectInstructionProgress()` 计算本批规则进展调用的集合。只有非空可信版本键对应的完整片段保留时，相关内置修改工具的 `not_started/precondition` 等待才视为新证据；同一集合供失败记忆、纠错恢复和默认轨迹跟踪共用，后两者不再根据原始输出重新推断。规则等待不写入普通重复失败记忆，不消耗文件条件纠错额度，也不产生“不要重复未变化失败”的轨迹提示；对外仍保留真实的 `isError/precondition/not_started`。同批 Read 交付规则、Write 只有空键列表的渐进等待也适用。`hostProjectInstructionHardLimit` 仅由受检入口在清洗自由 metadata 后接受可信内置事实，硬上限等待即使遇到同批其它规则进展也不豁免。没有新片段的空键等待、预算裁剪掉正文及普通 Write 冲突仍受原重复失败和纠错保护；没有把 Write 标为全局可安全重试。实际模型轮次、用量和运行硬限制照常计数。

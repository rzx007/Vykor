# 工具管理与执行

处理工具从注册、向模型展示，到检查参数、获取权限、执行和返回结果的完整过程。

| 文件 | 用途 |
| --- | --- |
| `tool-registry.ts` | 保存工具定义、校验注册，按可见范围生成运行和模型使用的工具集合 |
| `tool-discovery.ts` | 在本次运行内发现和启用工具 |
| `tool-definition-identity.ts` | 为同一工具定义提供稳定标记，供绑定和授权校验使用 |
| `tool-input-schema.ts` | 规范工具输入并按参数定义检查 |
| `tool-input-reuse.ts` | 从历史成功调用中复用允许复用的输入 |
| `query-tool-preparation.ts` | 解析和检查输入，区分可执行调用与应直接返回的错误 |
| `query-tool-permissions.ts` | 处理权限、执行前后的回调，以及工具状态事件 |
| `query-tool-limits.ts` | 工具超时和输出大小限制 |
| `tool-execution-context.ts` | 为工具组装当前执行环境与可见工具集合 |
| `checked-tool-execution.ts` | `executeCheckedTools()` 串联准备、授权、分组执行和结果交付 |
| `operation-execution.ts` | 保存不可变工具意图，检查宿主安全能力，限时执行强制规则，阻止回执保存失败后的危险调用 |
| `tool-failure-memory.ts` | 记录失败输入和证据版本，识别未发生变化的重复失败 |
| `tool-batch-recovery.ts` | 完整批次交付后，计算纠错次数、恢复额度和是否要求模型收尾；额度耗尽时抛出现有错误 |
| `tool-result-feedback.ts` | 将执行结果、失败提示和文件事实整理成模型可读取的内容 |
| `__test__/` | 上述规则与引擎中的工具执行集成测试 |

`QueryEngine` 将模型生成的工具调用交给 `executeCheckedTools()`。输入检查通过后才进行授权与执行，输出结果返回引擎写入消息历史，供下一轮模型使用。

受检执行返回两条独立通道：`results` 保存每个工具的结果，`fatalFailure` 只保存无法可靠继续运行的宿主或运行错误。超时、工具普通抛错和 `unknown` 结果不进入致命通道；错误、已有输出和恢复提示写入历史后交给模型继续处理。SDK 的 `executeTool()` 和嵌套 `invokeTool()` 也返回这些工具错误，仅在致命失败时抛出。运行限额、操作记录保存失败、调用跟踪失败或生命周期交付失败仍在完整结果交付后传播。模型循环收到运行取消后停止请求；SDK 显式调用仍按原契约返回 `interrupted` 错误结果。

创建工具上下文时，执行器传入宿主致命失败上报能力和启动门禁。嵌套受检执行通过 `onFatalFailure` 连接父调用，在保存错误、调用跟踪或生命周期交付失败时立即上报，不依赖代理工具是否捕获了异常。`dispatchSignal` 只控制新调用的启动，不取消已经开始的调用；代理捕获故障后再次调用工具也不能绕过父门禁。这些能力仅在执行器之间传递，不从工具返回数据中读取；父批次停止尚未启动的调用，已开始的调用仍分别保存回执。

批次结果全部写入历史并交付 `tool_use_end` 后，引擎先检查执行失败、取消和成功结束运行的内部工具，再调用 `decideToolBatchRecovery()`。它先检查参数与文件条件的纠错上限，再通过回调观察轨迹，最后检查重复失败的恢复额度；纠错已达上限时不观察轨迹，恢复额度耗尽时仍观察本批结果。成功与失败混合批次可以解除重复失败恢复，但只有全部成功才清零两类纠错次数。计数和剩余额度仍由本次 `submitMessage()` 保存，普通函数只返回下一轮状态或抛出错误；逐条失败记忆、证据版本和结果保存留在引擎原位置。`__test__/tool-batch-recovery.test.ts` 覆盖这些顺序边界。

参数别名只在工具顶层识别，例如把 `filePath` 对应到 `file_path`；嵌套对象和数组项作为业务 JSON 按声明检查，不推断别名。结构化交付中的 `data.path` 与允许的额外字段 `data.file_path` 可以分别表示来源和目的路径，不能因此被误判为同一个参数。

`ToolContext.toolResults` 是宿主已按当前 Run 和工具来源绑定的异步结果读取能力，供内置 `ToolResult` 查询使用。旧的同步 `readToolResult()` 仍只读取当前 Run 中有限大小的结果，并核对原插件来源和捕获的执行函数，不转为跨 Run 全库访问。`tool-result-feedback.ts` 生成的补读提示在正文预算处理后添加，自由工具元数据不能伪造引用。

宿主提供 `AgentExecutionContext.toolSafety` 时，模型调用、显式 `executeTool()` 和工具内部 `invokeTool()` 都按同一流程执行：规范输入并校验 → 保存操作 → 普通权限 → 强制规则 → 用户审批与可选 Hook → 派发前再次检查强制规则 → 保存派发记录和真实尝试编号 → 调用工具 → 保存完整结果 → 发布状态与交付结果。操作账本由宿主保存；core 只保存当前批次的调用状态，并在同一宿主与 Run 的回执保存失败后禁止继续危险调用。可信只读操作仍可用于核对状态。工具返回的错误不能证明写操作未产生部分效果。

操作输入使用同一份不可变快照，审批与实际调用不会看到不同参数。关闭可执行 Hook 或使用内部工具不会跳过强制规则。规则拒绝、抛错、超时、缺少成对能力或调用期间取消时，都不允许派发；默认规则等待上限为 5 秒。普通执行前 Hook 抛错仍按原约定放行。

已确认操作直接复用账本中的完整结果；未知结果不会自动重放。工具超时或取消后，已经开始的其他调用仍分别保存回执。不配合取消的工具若随后返回，core 只补存迟到回执，不再次交付模型或重开运行；补存失败通过宿主诊断事件报告。嵌套调用拥有自己的操作和真实尝试编号，并记录父操作关系。独立 SDK 不提供 `toolSafety` 时沿用原执行流程，不创建数据库。

重复派发尚未解决的操作属于策略拒绝，作为工具反馈交付，不因此结束整轮。同一串行组里的后续调用仍被拦截，独立工具可继续。宿主账本继续拦截同一会话树中未确认写入之后的危险操作，可信只读操作可用于核实；换调用 ID、工具名或先完成一次读取均不能解除写入保护。任意 Shell 命令仍按可能写入处理，不能仅凭命令文字或工具的自由声明授予只读身份。迟到回执或宿主核对确认解决后，才恢复写入资格。

宿主提供 `observeInvocation` 时，受检执行在工具真正调用前登记它的实际结束 Promise。该 Promise 跟随工具本身的成功或拒绝，超时和外层取消不会提前结束它；登记抛错会阻止工具启动，并清理超时计时器与取消监听。它不根据结果的 `failureKind` 或自由 metadata 推断调用是否仍在运行。

工具定义保存在 `ToolRegistry` 实例中；发现状态、失败记忆和授权上下文跟随本次运行。文件读写、命令执行等具体工具实现放在 `@vykor/tools` 等提供方包中。新增工具执行规则放在本目录，测试放在同层 `__test__/`。

`trusted-read-only-identity.ts` 保存可信宿主明确登记的定义身份和原始 `execute` 函数，冻结后的运行副本必须同时匹配二者。混合查询和写入动作的工具还可登记输入判断函数；宿主须传入本次操作已经规范和冻结的实际输入，只有匹配的调用才获得只读身份，省略输入不会把整个工具放行。它不读取工具名、`safeToRetry` 或 `readOnlyHint`；来源是否为内置工具或宿主追加工具，以及当前调用是否匹配捕获绑定，由 Server 另外检查。原 `ToolResult` 身份标记仍独立用于排除查询工具自身的归档。

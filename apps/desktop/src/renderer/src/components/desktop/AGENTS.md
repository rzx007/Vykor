# Desktop 目录协作约定

本目录按用户功能分类。新增或迁移文件时，沿用以下规则。

## 文件放在哪里

- 先阅读所在分类的 `README.md`，复用现有分类；只有出现独立职责时才新增目录。
- 根目录只放总说明和协作约定。页面入口放在对应的 `*-page` 目录，桌面全局事件和快捷键放在 `shell`，窗口与面板布局放在 `layout`。
- 优先按功能组织组件、状态转换、类型和 hook，让一起修改的文件放在一起；不机械拆成 `components`、`hooks`、`utils` 三层。
- 一个分类明显变杂时，再按子功能拆分；不要给每个单独文件都套一层目录。
- `shared` 只放当前分类内确实被多个功能复用的代码。已有基础 UI 继续复用 `components/ui`，不要把不相关代码塞进 `shared`。
- 保留清楚的文件名，如 `provider-connection-dialog.tsx`、`note-save-coordinator.ts`；不要靠目录名掩盖含糊的 `helpers.ts`、`common.ts`。

## 测试与引用

- 对应测试统一放在被测代码同级的 `__test__` 目录；测试数据、辅助模块和基准测试也放在那里。
- 测试文件保留被测功能名称，使用现有的 `.test.ts` / `.test.tsx` 命名。
- 迁移时同步更新静态导入、动态导入、测试 mock、CSS 与测试辅助文件引用；不留下旧路径的转发文件。
- 分类内部可用相对路径，跨分类优先使用项目现有的 `@renderer` 别名。只在需要稳定对外入口时保留 `index.ts`，不新增汇总所有内部组件的导出文件。
- 目录整理与行为修改分开进行。按影响范围运行类型检查和相关测试，不为了整理目录改动业务逻辑。

## 分类说明

- 每个功能分类及其子分类都维护一份 `README.md`；`__test__` 不必单独建说明。
- README 写清职责、哪些文件应该放入或移出、主要入口和子目录。避免复制组件实现或罗列容易过时的全部文件。
- 新增分类、移动入口或调整边界时，同步更新该分类及父级 README 的导航。
- UI 实现继续遵循 `apps/desktop/DESIGN.md`，复用已有组件；目录整理不主动搭建预览或截图。

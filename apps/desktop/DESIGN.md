# Vykor Desktop 设计基线

Vykor Desktop 的界面应当安静、可靠、精确。它是一款需要长时间停留的开发工具，不是营销页面，也不是由一组仪表盘卡片拼起来的后台系统。

这份基线参考 Codex 等现代桌面开发工具的结构与密度，但不照搬具体页面。新增页面和改造旧页面时，应优先保持 Vykor 自己的任务流一致。

## 1. 页面结构

- 应用外壳负责侧栏、工作区边界和全局导航；页面内容不要再套一层“大卡片”。
- 设置、插件、任务管理等阅读型页面使用居中的可读内容列，推荐最大宽度 `56rem` 左右。
- 页面标题与正文靠留白建立层级。页面标题默认约 `20px / 600`，区块标题约 `15px / 600`，说明文字约 `12–13px`。
- 同一页面只保留一个主标题。不要用多个大标题重复描述相同的信息。
- 设置先展示实际状态和常用偏好，低频参数、技术路径与维护操作按需展开；已保存、实际生效和未完成检查不可混为一谈。

## 2. 表面、边框与阴影

- 默认表面是工作区背景。设置页按用户使用场景分组，允许用轻量卡片划分“对话与任务”“应用与提醒”等功能组，内部使用紧凑设置行与细分隔线。
- 卡片用于明确功能边界，不为每个设置或数字单独建卡，也不嵌套卡片。常用设置优先展示，低频配置、系统排查和迁移操作置于高级分区。
- 列表优先使用行间距和细分隔线，不要把列表再装进带圆角和阴影的大容器。
- 边框用于表达输入范围、窗口边界、可点击区域或状态边界；没有这些含义时就不要加。
- 不在同一个层级同时叠加背景色、边框、大圆角和阴影。
- 页面内部通常不使用阴影。应用外壳、浮层和菜单可以保留克制的阴影来表达层级。

## 3. 控件

- 主要操作才使用实心按钮。刷新、重新加载、更多操作等低风险动作优先使用 ghost 按钮或图标按钮。
- 搜索框、文本输入框保留清晰边界，因为边界表达了输入范围；不要额外添加外层卡片。
- 筛选使用线型标签或轻量分段控件。避免在页面中重复出现厚重的胶囊背景。
- 开关只用于立即生效的二元状态；破坏性操作必须经过确认。
- 下拉框显示用户可理解的标签，不显示 global、native 等内部值；数值和选择控件保持紧凑宽度，不挤压左侧名称。多字段编辑明确使用保存/取消，保存栏仅在有修改时出现，切换范围保护未保存草稿。

### 组件选型

- 先复用项目已经接入、符合本规范的组件。需要新组件时，优先通过 beUI MCP 和 `beui` Skill 查找适合的现成组件，尤其是聊天、浮层、侧边面板、通知和状态反馈。
- 交互和可访问性要求都能满足时，优先采用 beUI。选定前读取组件用法、源码和依赖，确认适配当前 shadcn Base UI 组件及 `@renderer` 路径别名。
- 通过已配置的 `@beui` registry 接入时，先核实实际安装名称；保留项目已有的工具函数、组件修改和行为。
- 接入后的颜色、字体、圆角、间距和图标沿用本规范。动效主要服务于展开、收起、切换与反馈，遵循下文的动效尺度，并支持系统的减少动态效果设置。

### 工具栏、搜索与浮层

- 浏览器、便签、侧边聊天和插件交互共用这套控件规则。工具栏高 `56px`，内部按功能分组，组间留 `8px`；不要把每个操作都装进独立卡片。
- 独立文字操作使用 `Button shape="pill"`，图标操作使用 `shape="circle"`。常用控件高 `32–36px`，小号操作至少 `28px`；全圆角仅用于这些小控件，不用于整页容器。
- 浏览器导航、浮动文字操作等紧密相关的操作使用 `ButtonGroup variant="toolbar"`：一条浅边框、胶囊外形，组内按钮使用 ghost。独立工具按钮使用 `variant="control"`，阴影统一来自 `shadow-control`。
- 搜索框、浏览器地址栏使用 `InputGroup shape="pill"`，标签必须可被辅助技术识别。搜索与主要的新建操作保持同一高度；新建使用主题里的 `primary` 实心按钮。
- 选中状态优先用轻背景和明确的图标、文字反馈；批注工具使用 `variant="annotation"` 和 `aria-pressed`，暖色只表达批注模式。焦点、禁用、加载状态不得被圆角或颜色调整遮掉。
- 批注编辑器、批注列表和文本选区浮层使用 `popover` 表面与 `16px` 圆角、克制阴影。普通便签列表与插件结果不使用浮层阴影。
- 便签正文使用默认 UI 字体，保留足够行距；等宽字体仅用于代码、路径和真实的结构化数据。

### 图标

- 使用现有 `lucide-react` 图标，工具控件的线宽统一为 `1.75`，常规图标 `16px`，紧凑操作 `14px`。不为这次改造引入另一套图标库。
- 优先选择语义相同的圆形版本，如 `MessageCirclePlus`、`MessageCircleMore`、`CirclePlus`、`CircleCheck`、`CircleStop`；Lucide 的旧别名也可能以 `Circle` 结尾。
- 图标含义优先于外形。便签、文件、文件夹、复制、删除等保留准确的图形；关闭、方向和缩放图标置于圆形按钮时不额外套一圈图形。
- 图标按钮提供 `aria-label` 和提示文字，带文字的按钮给图标标记 `data-icon="inline-start"` 或 `inline-end`。

## 4. 状态反馈

- 保存、刷新、导出等操作的成功提示统一使用已有 toast，不在设置正文中插入成功提示。首次加载与后台自动刷新不弹成功 toast；校验错误、不可用原因和等待重启等持久状态留在对应位置。
- 警告和错误可以使用 Alert，因为它们需要打断注意力；同类信息应合并，避免连续堆叠多个边框框体。
- 加载骨架应模拟最终内容的形状和密度，不显示一个巨大的空白卡片。
- 空状态保持紧凑，说明下一步能做什么；不要用大面积边框把“没有内容”放大成页面主体。
- 功能关闭时隐藏依赖的参数表单，保留已保存的值。需要先配置才能启用的功能提供“设置并启用”入口，展开或取消配置都不自动启用；破坏性操作仍须确认。

## 5. 列表与详情

- 列表行默认高度控制在 `56–72px`，主要信息一行、次要信息一至两行。
- 图标是识别线索，不是装饰海报。常规插件或工具图标建议为 `36–40px`。
- 状态徽标只表达异常、待处理或重要状态。来源、范围等普通元数据优先使用次要文字。
- 详情弹窗内部使用标题、间距和对齐建立分组；不要为每个小分组再创建灰色圆角卡片。

## 6. 颜色、字体与动效

- 统一使用现有语义颜色变量，如 `background`、`foreground`、`muted`、`border` 和 `destructive`，不要在业务页面写固定颜色。
- 主题遵循 shadcn/ui 的变量约定。用户设置的强调色对应 `primary`，用于主要操作与焦点；`accent` 和 `sidebar-accent` 是轻量交互底色，列表选中与悬停不随强调色染色。
- 背景直接控制工作区。侧栏、浮层、输入边框和选中底色从背景派生；玻璃外壳使用同一派生色作为染色层，保留原生透光控制。玻璃只在 macOS / Windows 上提供，Linux 没有系统原生材质，固定为不透明，外观页也不展示该设置项。
- 前景是正文、控件和侧栏文字的共同来源，各层级通过不同混合强度调整深浅，不对整个文字容器设置透明度。正文、次要文字与链接保留可读对比度；用户选择的前景过于接近背景时，自动提高文字对比度，并在外观设置说明实际颜色。
- 浅色与深色的背景、前景分别保存，跟随系统时自动切换；启动与运行期使用同一套颜色派生逻辑。文字选区使用独立的 `selection` 变量，侧栏更明显的选中底色沿用 `sidebar-selected`。
- 正文和控件使用应用默认 UI 字体。展示字体只用于确有品牌表达需求的场景。
- 动效服务于状态变化，常规时长控制在 `150–200ms`。尊重系统的减少动态效果设置。
- hover 只做轻微背景或文字变化；不要使用缩放、发光或大幅位移制造反馈。

## 7. 提交前检查

- 是否存在可以直接删除的外层 Card、Alert 或边框？
- 是否有超过一个页面级大标题？
- 信息层级能否只靠标题、间距和字体粗细读懂？
- 成功状态是否比错误状态更抢眼？如果是，应降低成功状态的视觉重量。
- 空状态是否占据了过多页面面积？
- 深色模式、键盘焦点、缩放和窄窗口下是否仍然可读、可操作？

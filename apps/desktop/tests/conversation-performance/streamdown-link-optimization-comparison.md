# Streamdown 链接处理：小范围优化与对比

2026-10-29，基于 Streamdown 2.7.0，对比本次修改前后的生产构建。只做两项优化：链接与行内代码渲染器移除内部 `node` 属性；通过 pnpm 补丁跳过 `rehype-harden` 把通配符 `*` 当作 URL 解析的尝试。没有改动分块、刷新调度、逐字动画或列表解析边界。

## 测量条件

- Electron 39.8.10 / Chromium 142.0.7444.265，Windows，隐藏窗口，关闭 GPU。
- 沿用 [markdown.tsx](markdown.tsx) 的实际 `AssistantMarkdown`、外观设置、输入、容器尺寸和动画 CSS。没有加载完整应用样式，绝对耗时不代表所有真实会话。
- 修改前构建基于 `55af72d4` 的 Markdown 实现；先保存完整构建，再应用优化。核对两个入口 bundle，差异仅为本次优化和构建引用名。没有同时升级其他依赖。
- 每轮两次预热，再执行一次不计时的追加以统计 DOM 属性写入；等待动画清理后，测量八次追加。每次都等待新文字真正显示。
- 四轮采用 A/B、B/A、A/B、B/A 顺序，每种状态每个构建共测 32 次更新。计时区间内不运行 CPU 采样器、URL 包装或 MutationObserver。
- 指标为 Chromium `TaskDuration` 增量除以实际更新次数，包含流式更新和动画清理，排除挂载、预热、属性诊断和最终静态渲染。

## 确定消除的重复工作

| 检查 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 2,000 项带链接列表，每次追加的 `node` 属性写入 | 2,000 次 | 0 次 |
| 800 组行内格式段落，每次追加的 `node` 属性写入 | 800 次 | 0 次 |
| 25 个普通网页链接，URL 构造参数包含通配符 `*` | 存在 | 不存在 |

前两项由真实 Electron DOM 的单独诊断追加确认；最后一项由真实 Markdown 流程的回归测试检查，保留原生 URL 构造行为，只记录调用参数。

## 链接校验阶段的单独对照

在同一个 Electron 页面中，分别加载原版和补丁版 `rehype-harden`，使用含有 2,000 个链接及加粗、普通文字的列表语法树。每次新建输入，建树不计时；先各预热八次，再交替执行 32 次。只计校验插件的同步执行，不包含 Markdown 解析、React 或布局。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 每次处理平均耗时 | 33.9ms | 11.6ms |
| 单次范围 | 28.7～46.6ms | 9.6～17.8ms |

这个阶段平均减少约 66%。每次处理后同时核对链接地址及 `noopener noreferrer`，没有绕过安全校验。这只是局部阶段的收益，不能解释为整条渲染链路快了 66%。

## 完整渲染对照与限制

四轮平均每次更新的 UI 主线程耗时：

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 约 10.4 万字符纯中文段落，动画开启 | 83.2ms | 68.2ms |
| 800 组加粗与链接的段落，动画开启 | 346.0ms | 499.8ms |
| 2,000 项连续列表，动画开启 | 991.5ms | 804.6ms |
| 2,000 项连续列表，动画关闭 | 697.9ms | 794.5ms |

结果有明显反向变化，不能据此认定整体提速。尤其是没有受到这两项优化影响的纯文本对照也变化约 18%；列表动画开启的修改前各轮均值在 451.1～1,342.9ms 间波动。

为检查波动，另外把本次测试进程及继承的渲染进程限定在同一个逻辑 CPU，采用 A/B、B/A 各八次更新复测。此限制只作用于独立测试进程，退出即结束：

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 富文本段落，动画开启 | 294.2ms | 332.4ms |
| 长列表，动画开启 | 924.5ms | 660.8ms |
| 长列表，动画关闭 | 570.6ms | 672.9ms |

复测仍有反向结果，单轮方向也不一致。仅靠这两组跨进程结果，无法证明稳定的整体收益，也无法排除回退，因此继续进行同一页面的补充验证。

## 同一页面的补充验证

在保存的修改前 bundle 中，仅给本次两项处理加上临时开关，始终使用同一个 Electron 页面和渲染进程。开关关闭时执行原逻辑，打开时执行本次优化；每种状态都重新挂载相同输入、预热两次、测八次更新，四轮交替顺序，共各 32 次更新。本组不执行额外属性诊断追加，数值只在本组内比较。临时开关与执行脚本位于忽略目录，不进入产品代码。

这组实验用于减小进程和运行状态差异；临时条件判断也带来额外开销，因此不能替代上面的真实构建对比。

| 场景 | 原处理逻辑 | 启用两项优化 | 平均降幅 |
| --- | ---: | ---: | ---: |
| 富文本段落，动画开启 | 471.0ms | 456.1ms | 约 3% |
| 长列表，动画开启 | 770.7ms | 643.2ms | 约 17% |
| 长列表，动画关闭 | 744.9ms | 684.7ms | 约 8% |

长列表开、关动画的四轮配对均有下降；富文本段落有两轮反向变化，不把约 3% 视为稳定收益。每组长列表仍有 32 个超过 50ms 的任务，优化没有消除长任务。

综合这些结果，可以确认减少了重复工作，同页诊断支持长列表开销下降，但跨进程真实构建尚未得到稳定的整体降幅。长列表的整段解析成本仍然存在；本次没有为了得到更好数字而修改输入、跳过输出或增加刷新调度。
